## 为什么有第二期
第一期的 X1–X8 已全部落地（X1 v3.65.0 / X2 v3.66.0 / X3 v3.67.0 / X4 v3.68.0 / X5 v3.69.0 / X6 v3.70.0 / X7 v3.71.0 / X8 v3.72.0）。第二期不再增加孤立 App（当前 81 个 App 目录、82 条 APPS id 已有规模），而是把已有底座串成**用户能完成的一件事**，并补上长期使用真正需要的能力。

## R-X1 · 统一行动中心与跨 App 通知箱（P1，规模 L）
**需求**：日历、社媒、财务、续玩、记忆相关事件分散在不同 App，用户无法从一个地方看到「现在该处理什么」。

**功能**：
1. 汇总五类待处理项：待确认账单、到期约定、未读事件、续玩建议、失败任务。
2. 每条带来源 App、来源事件、会话、楼层或剧情时间。
3. 支持完成 / 延期 / 忽略 / 跳转原处四种动作。
4. 「只读通知」与「需要确认的通知」分开呈现。

**验收**：
- 同一事件跨 App 不重复生成通知（按来源事件键幂等）。
- 通知点击能打开真实来源，跳不过去要说清原因。
- 免打扰只抑制展示，**不丢失事件**。
- 回档后未来通知可撤回或标记过期。

**依赖**：R-O7（诊断处置入口）、R-O3（会话身份）。

---

## R-X2 · 跨 App 来源链与实体关系浏览器（P1，规模 L）
**需求**：全局搜索能找到内容，但用户还不能看到一条信息如何从原始记录流转到通知、草稿、记忆或生成请求。

**功能**：
1. 以事件、角色、交易、素材、楼层为节点，展示来源 / 派生 / 转述 / 引用 / 当前状态。
2. 从手机记录跳到原始出处（无跳转能力时给可执行的替代定位）。
3. 同名异人、不同会话、不同分支**明确隔离**。
4. 与第一期 X5 已交付的社媒知情边界（`social-knowledge-bridge.js`）共用同一份可见性判定，避免两套口径。

**验收**：
- 每个展示节点都有稳定 `ref`，或明确标注「不可长期定位」及原因。
- 派生内容不得冒充原始事实。
- 删除或撤回源记录后，下游显示失效状态而不是静默消失。
- 不能通过关系图跨会话 / 跨分支泄露内容。

**依赖**：R-O3、上游 X1（结构化证据查询）。

---

## R-X3 · 财务与事件的确认提交向导（P1，规模 L）
**需求**：财务总览与旅行结算草稿已交付，但「建议」与「真实落账」之间还缺一个稳定、可重试、可撤销的用户闭环。

**功能**：
1. 预览交易：来源、币种、参与者、重复风险。
2. 用户确认后交给**唯一账本 owner** 写入。
3. 写入后回读确认；失败可重试或撤销。
4. 区分「已发生 / 待确认 / 模拟报价 / 结算建议」四种状态。

**验收**：
- 预览不修改余额。
- 同一草稿重复确认不重复扣款（幂等键）。
- 多币种不得盲目相加；不同账户不得混算。
- 仅「建议转账」不得被上游记成已付款。

**依赖**：R-O4（写入回执）、上游 X4 / X6。

## R-X4 · 跨项目续玩工作台（P1，规模 L）
**需求**：本仓已有续玩简报、分支对照、受控恢复交接；上游已有长篇分卷与接续包。两者尚未连成一条用户流程。

**功能**：
1. 显示项目、卷、章节、当前分支、最近停点。
2. 汇总未了事项、角色状态、剧情时间、财务、可接续证据。
3. 三级操作：只读查看 → 生成接续草稿 → 请求恢复。
4. 恢复仍委托真实 owner，手机侧不得自行篡改主档。

**验收**：
- 未选择项目时维持会话完全隔离。
- 同名角色、不同宇宙不合并。
- 接续前显示冲突、缺面与影响范围。
- 恢复后回读结果；旧异步写入被拒。

**依赖**：R-O1、R-O3，上游 X7（分卷与选择性接续）。

---

## R-X5 · 安全的声明式个人工作流（P2，规模 L）
**需求**：用户已有 81 个 App，很多操作需要手动串联。可以引入自动化，但**不允许用户脚本直接改手机状态**。

**功能**：
1. 声明式步骤组合，例如「生成续玩摘要 → 保存草稿 → 发通知」「确认账单 → 更新日历事件」。
2. 每步声明输入、输出、权限与 owner。
3. 支持预览、暂停、重试、回滚。
4. 不执行任意用户 JavaScript（沿用本仓既有结构约束）。

**验收**：
- 默认 dry-run；写操作必须显式确认。
- 重试幂等；某步失败不得假装整个流程完成。
- 跨会话时工作流必须重新确认身份。
- 新模块进入既有扫描面（registry / keys / lifecycle）。

## R-X6 · 素材到发布的完整创作工作台（P2，规模 L）
**需求**：X6 已实现「素材到草稿」，X7 已实现多角色生图。下一步把素材、角色、事件、目标 App 与发布前检查真正连起来。

**功能**：
1. 角色 / 事件 / 图片 / 曲目 / 文本统一素材选择（含生图队列产出的图像）。
2. 显示来源、授权备注、版本、缺失资源。
3. 生成目标 App 的可编辑草稿。
4. 发布前检查：敏感内容、缺图、坏链接、目标权限。
5. 发布动作仍由目标 App owner 执行。

**验收**：
- 素材可回溯到来源 ID。
- 缺播放器 / 坏图 / 缺权限不得显示发布成功。
- 本地资源完整可用（不引入新的网络前置）。
- 同一曲目、图片、生成任务不复制出多个状态源。

## R-X7 · 本地备份、迁移与灾难恢复（P1，规模 L）
**需求**：手机数据主要存本地，长期使用后需要安全导出、迁移与回滚。

**功能**：
1. 按 App / 会话 / 项目 / 素材选择导出范围。
2. 备份包含 schema 版本、来源、会话范围、分支范围、敏感字段标记。
3. 支持预览、冲突检测、部分导入、撤销。
4. 默认不上传云端。

**验收**：
- 导入前不修改现有数据。
- 旧版本包明确迁移或明确拒绝（不得静默丢弃字段）。
- 同一记录重复导入幂等。
- 会话与分支边界不能被备份导入打穿。

**依赖**：R-O4。

---

## R-X8 · 宿主与能力健康中心（P1，规模 M–L）
**需求**：功能是否可用取决于 SillyTavern 版本、记忆插件版本、模型通道、图像通道与浏览器能力，当前缺少统一可见性。

**功能**：
1. 展示宿主版本、插件版本、可用 API、缺失能力、降级模式。
2. 对搜索、记忆、图片、语音、通知、恢复交接分别给出状态。
3. 提供「复制诊断报告」按钮。
4. 双项目版本不匹配时给出明确联动提示（读 `crossrepo-registry.js`）。

**验收**：
- 每项能力分为：可用 / 部分可用 / 不可用 / **未验证**（四态不同形）。
- 缺能力时给替代操作，不把「接口存在」报成「服务可用」。
- 能力检测本身不得触发真实写入或模型调用。

---

## R-X9 · 无障碍、窄屏与个性化操作层（P2，规模 M）
**需求**：功能规模已很大，继续增加入口会抬高使用成本。

**功能**：
1. 任务入口、收藏、最近使用与键盘 / 触摸可达性统一。
2. 字体缩放、紧凑列表、低动画、深色模式。
3. 重要状态不只依赖颜色。
4. 320px 窄屏专门布局。

**验收**：
- 核心操作可通过键盘与触摸完成。
- 放大字体后不遮挡按钮与状态。
- 空 / 未知 / 失败 / 成功有文字或图标辅助。
- 设置重开后保留，且按会话正确隔离。
