# Agent Note: RubyPhone 拓展计划（深度、广度与新功能）

Status: proposed

## Problem

素材路线已扩大到 81 个 App，但“可以打开一个案头”与“在手机里完成一件事”之间仍有距离。本轮复算六面命中为注入 28 / 搜索 27 / 通知 14 / 微信链路 10 / 上游读数 12 / 生命周期 65。32 件只命中生命周期；这个数是任务筛选线索，不能直接当 32 处缺陷。

当前代码已有续玩简报、多角色生图 payload、九账读数、周期算法、旅行分摊和多种内容案头。拓展应利用这些底座，每批交付完整操作流程，避免再造同名空壳。基线为 RubyPhone v3.56.0 / `ac0a570`，配套记忆插件 v3.271.0 / `1a0ba36`；本计划为提案，未实施。

## Proposal

### X1 · 任务入口与最近使用（广度深化，P1，规模 M）

现状：已有桌面分页与自由布局案头；不能默认自由布局案头已经控制真实桌面。81 件入口对日常找功能的成本很高。

内容：在真实桌面提供按任务导航、收藏、最近使用和能力筛选，例如“找一段往事”“整理素材”“今天有哪些事”“管理余额”；既有 App 保留独立入口，任务入口只是聚合。自定义组件先做受限声明式卡片，读现有 App 的投影与动作白名单，不执行用户 JS。

验收：任务入口能导航到真实 App 并定位具体页签；收藏重开保留、切聊遵守既有 scope；读不到的卡片说清原因；布局修改在真实桌面可见，不能仅改案头预览。依赖优化 O1/O5。

### X2 · 跨 App 检索与精确打开（广度深化，P1，规模 M–L）

现状：已有全局搜索和覆盖度，消费矩阵仅 27 件 F2 命中；不少新内容桶未进入平台搜索。现有结果也不等于都能定位原条目。

内容：按内容价值先接旅行费用、总结册、纪念日、曲库、创作收藏；规则工作台、布局参数等保持定向检索或明确不适用。结果带 App、itemId/ref、会话、楼层/剧情日与版本，支持打开到原条目、回看出处；无宿主跳楼能力时提供可执行的替代定位，不声称已跳到楼层。

验收：每个新增源以真实存储形状 seed 命中，打开后定位同一 id；删除、编辑、切聊后结果不陈旧；只为适用源登记，不能为了把矩阵涂满而索引所有设置。依赖 O2/O4。

### X3 · 剧情日程与提醒联动（深度深化＋新流程，P1，规模 L）

现状：health、calendar、periodmath、annidate、date/loverspace 各有能力，周期数学与纪念日数学目前仍是案头。三源剧情时间已有 story-clock，对不上时有冲突读数。

内容：把算法输出转换为用户可选择的日历建议，统一查看纪念日、约会、周期事件与未了约定。剧情时间推进触发剧情提醒；现实番茄钟等仍走现实时间，不能混用。重复计算同一来源事件按幂等键更新，取消来源后撤回对应提醒；健康预测与剧情既定事实分开标识。

验收：剧情日推进→事件到期→通知落账→点开原条目全链成立；免打扰只抑横幅、不丢账；回档撤销未来提醒；缺剧情钟不拿今天顶替。依赖 O3/O4；可独立安装手机，不强制记忆插件。

### X4 · 财务总览与旅行结算交接（深度深化，P1，规模 L）

现状：wallet 显示记忆插件金钱账，asset/accounting/piggy/shop/taobao/traveldesk 各持不同语义。traveldesk 实际处理费用、家庭归并、内部/外部债务，**尚不能称为行程系统**。

内容：先建只读资金总览，按来源显示余额、消费、待收/待付，区分真实已发生、模拟报价、结算建议。旅行分摊生成带参与者和币种的结算草稿；用户选定一个真实账本接受后才落账，其他来源保留引用。新“行程管理”若另做须建独立模型与日程关系，不拿费用账冒充。

验收：同笔交易跨 App 展示不重复计总额；不同账户和币种不盲目相加；预览不改余额，确认只由一个 owner 写；重试不重复扣款；仅建议转账不会被上游记成已付款。依赖 O5，与记忆插件 X4 协同。

### X5 · 社媒知情边界实际接入（深度深化，P1，规模 L）

现状：socialguard 已有受众、人脉、seenBy、分身与互动判定，目前定位“熟人可见性案头”，不能当作微信/社媒实际拦截器；其读数不一致先由 O3 修复。

内容：将同一份可见性判定用于选择性接入的朋友圈、角色回复、通知收件人和生成上下文。分清玩家可看与角色已知；公开、转述、私聊分别记录传播出处。先做朋友圈一条端到端链，再扩其他平台，跨平台转发保持同一事件来源，不能凭转述数增加可信度。

验收：看不见帖子的人不从搜索、通知、AI 回复另获内容；未看不能互动；撤回、换分身、修改受众后缓存失效；未知权限保留未知。用户可检查谁在哪个剧情时刻获得了哪条信息。依赖 O3/O4，与记忆插件 X5 联动。

### X6 · 创作素材到发布草稿（广度深化＋新流程，P2，规模 L）

现状：musicdesk、stickerdesk、soundkit、pixiv、lofter、magazine、pvdesk、doujin 分散管理素材或读数；musicdesk 明确零网络、零音频元件，本身不是播放器。

内容：串出“选角色/事件→选曲目/图像/表情/文本→预览→存草稿→选择目标 App”的创作流程。曲库选曲委托已有 MusicApp 播放；图像交给已有相册/生图队列，分享交给目标 App 的 owner。提供来源、授权备注、标签与版本；社媒先落可编辑草稿，发布动作显式触发。与织光机成信、杂志排版、纪念页形成复用。

验收：素材 id 可追溯，坏链接/缺播放器不显示成功；同一曲目不复制两份播放状态；重开草稿保留，切聊不串；纯本地路径完整可用。新网络服务须单独设计，不能作为本计划的隐含前置。

### X7 · 多角色生图操作深化（深度深化，P2，规模 M–L）

现状：image-generation-manager 已解析最多六个角色块、产生 v4_prompt/negative 坐标、多角色参考图与 vibe payload；从零增加多角色是过时前提。

内容：提供角色槽位编辑、主名/别名绑定、位置可视调整、参考图和一致性档案、共享提示词与逐角色差异，构建前显示最终角色分配。图片回执绑定会话/角色/场景；失败和重试走既有 nai-queue-worker，接相册与创作草稿。保持现有字符串语法兼容。

验收：六槽、增删重排、重复别名、坐标越界、缺参考图均有确定行为；payload 比对可离线验证；实际出图与角色一致性须在可用 NovelAI 账号和参考素材下另验，不能把 payload 合法当作图像验收。依赖 O4。

### X8 · 续玩与分支对照工作区（新产品流程，P1/P2，规模 L）

现状：已有 resume-brief 五面、织光机呈现、回滚预览、检查点内容对照、存档案头；它们已提供底座，不能重列成从零功能。

内容：把“上次停在哪→未了事项→相关证据→回到 App/出处”收成首页续玩卡。用户选两分支时呈现角色状态、约定、财务和剧情时间的语义变化；恢复前展示影响、缺面和会话身份，恢复只委托真实宿主/引擎 owner。先完成只读导航，再推进受控恢复交接。

验收：未知与空项分开，读数来自同一代会话；分支 A 的秘密不进入 B；内容对照不会改当前档；恢复前预检、恢复后回读，旧异步写入被拒。依赖 O1/O4，协同记忆插件 X2/X6。

## Alternatives considered

逐项补齐六条平台消费面能得到直观全覆盖，但很多工作台没有通知或自动注入的产品意义，且每项接入增加持久化与事件耦合，故按用户任务选接。把所有事实汇成第二份手机数据库能简化 UI，代价是来源漂移和与零数据库约束冲突，采用原 owner 取数＋只读聚合。重新移植外部完整手机能快速增加表现层，但 storage、自动请求和全局状态不兼容，保留当前底座逐条接入。

## Acceptance criteria

推荐三次大更新，每次都有完整用户流程：第一批 X1/X2/X3（找到功能并完成今天的事）；第二批 X4/X5/X8 只读部分（资金、信息边界与续玩）；第三批 X6/X7/X8 恢复交接（创作与分支操作）。X6/X7 可按使用频率调整顺序。

每项验收四面：算法结果正确、真实存储往返、用户入口可操作、失败可归因；涉及上游的再加独立安装与旧版本降级。不得以新增导出、菜单或测试数替代产品能力。关联[优化提升计划](../architecture/2026-10-04-optimization-plan.md)。

## Risks

自动联动可能将预测、草稿、报价误升为剧情事实；每一项必须有来源、状态和唯一写 owner。社媒权限必须同时约束检索与生成。多角色一致性依赖模型与参考图，不能承诺算法必然出同一张脸。分支恢复的 API 与宿主版本相关，实施前需精确核对可用出口。
