# Agent Note: RubyPhone 第十三期拓展创新计划
Status: proposed

> **期号口径**：本份为**第十三期**，编号 `R13-X*`。与记忆侧 `L13-X*`（`lonsha-memory-plugin`）配套。期号跳号的理由见 [优化提升计划](../architecture/2026-10-31-product-optimization-v13.md) 开篇 —— `R12` 已被 `docs/runtime-verification-boundary.md:380` 的「第十二条判据 R12」占用。
> **本轮只制定计划，不代表功能已实施或升版。**
> **纪律**：拓展项必须是**用户可感知的新能力**，不许是「把已有能力换个壳」。本份九项全部落在 `apps/` 或新 `config/` 内核 + 真入口，无一项是纯守卫/审计/台账。

---

## 0. 出发前提：先承认上一批拓展的真实结局

第六期拓展九项（R6-X1~X9）的声明状态是「历史已承接」，实测结局是 **9 件里只成 1 件**（`commission-pipeline` 被 `apps/creationdesk` 消费；其余 8 件在 `apps/` 零引用，`parallel-life` 只有中枢与沙盒引、`time-env` 恰有 2 处）。

这件事对本期拓展定了三条纪律，全部与「不许重演」有关：

1. **每项必须先有「在哪一个 app 里出现」这个答案，再开工。** 写不出 app 名的，本项不成立，直接不写进计划。R6 那 8 件的共同死因是「先做内核，界面留待以后」——以后没来。
2. **内核体积不许超 12K 字节而无界面。** 实测数据：`multi-activity-reroute` 13076 B、`club-coop` 11755 B、`story-reentry` 10044 B，三件都零引用。字节越多、越说明它当时是「认真做过的」，而认真做过的孤儿最难删——这是沉没成本陷阱。本期九项的内核预算每项 ≤ 12K，超出必须拆。
3. **每项交付必须包含一条「用户第一次能做什么」的具体句子**，且该句子在真浏览器场景里可被验证（依赖优化面 R13-O1 先接上浏览器门）。

## 1. 九项拓展

### R13-X1 · 一天：把散在各 app 里的事收成「今天」

**用户第一次能做什么**：打开一个叫「今天」的页面，看到**今天这一刻**在不同 app 里同时发生的事——几点收到了谁的消息、几点拍了张照、日程里有什么、日记写没写——**按时间轴排在一起**，点任一条能跳到原 app 的原位置。

- **为什么现在做**：这是本仓 88 个 app 的结构性缺口。当前每个 app 都是「自己的时间流」，用户要看「今天发生了什么」必须自己开五个 app 对时间。`apps/worldpulse` 有 `worldpulse-engine.js` 在做世界侧脉冲，但没有「我的今天」这个横向面。
- **内核** `config/today-timeline.js`（预算 ≤ 8K）：只做**聚合**，不做取数。各 app 通过既有数据层暴露一个 `todayEvents(): [{ at, app, id, kind, title }]`，本内核按 `at` 归并排序。**不发请求、不写盘**。
- **入口**：主屏新增一格「今天」，或挂到 `apps/clock` 内部一个页签（二选一，倾向后者——不增加主屏格子压力）。
- **依赖前置**：**必须先有 R13-O4 的时间单一源**，否则时间轴排出来的顺序是错的——这一条是硬依赖，不可绕。
- **撤销/降级**：某 app 未接 `todayEvents` 时，本内核按 `absent` 态显示「这个 App 还没接入今天」，不崩不空白（复用 R13-O6 的 reason code）。
- **定向回归**：造「一条消息 + 一张照 + 一条日程 + 一篇日记」在同一分钟，时间轴必须给出四条且顺序稳定（同一份数据跑两次逐字相同）；负控制：把其中一条的 `at` 改早，排序必须变。
- **诚实边界**：「今天」的边界如何定（0 点切 / 睡眠周期切 / 世界历切）当前**没有决定**，本项要求实施时**先定死并写进条目**，不许含糊。另外本项只做**只读聚合**，不提供「在这里直接回消息」——那属于 X3 的范围。

### R13-X2 · 有事找不着的「那时候」：跨 app 的模糊回忆检索

**用户第一次能做什么**：在全局搜索里输入「上次她说下雨那天」，能同时命中消息、照片（按拍摄时间与天气标记）、日记、朋友圈——且**结果里能看出每条为什么被命中**（命中的是哪个词、哪一天、哪个天气）。

- **为什么现在做**：`apps/search` 已有全局搜索（`search-app.js` / `search-view.js`），`apps/memory/global-search-engine.js` 是引擎。但它搜的是**文本**，玩家真实的记忆形态是「大约那阵子」「那天下雨」。这是本仓独有的优势面：它同时持有聊天、相册、日记、天气——**这个组合别的产品没有**。
- **内核** `config/vague-recall.js`（预算 ≤ 10K）：输入一个模糊条件（时间副词 + 天气 + 参与人 + 语义），输出候选条目 + 每条命中原因。**纯本地规则，不调模型**（要调模型就走宿主通道并如实标注「本轮用过模型」）。
- **入口**：`apps/search` 的搜索框下方「模糊回忆」折叠区。
- **撤销/降级**：只在既有搜索结果**之上追加**一栏，不改原搜索路径；模糊条件解析失败时退回普通搜索并在结果页顶部说明「没听懂这句，已按普通搜索处理」。
- **定向回归**：同一查询两次结果顺序稳定；每条结果必须有非空 `why`（命中原因）；负控制：把某条的 `why` 清空，判据须转红（**「命中但说不出为什么」等于没有命中理由**，与本仓「两种处境不许同形」同一条纪律）。
- **诚实边界**：「模糊语义」的理解质量**不在本项射程**——本项只保证「条件 → 候选 + 原因」这条链路上每步可回源。理解错不错由玩家自己看 `why` 判断，这也正是为什么要强制输出 `why`。

### R13-X3 · 消息里能「就地办」：从看到一句到做完一件事

**用户第一次能做什么**：在聊天里对方说「周六有空吗」，消息下方出现一个可点的动作条：加日程 / 回一句「有空」/ 记到备忘。点「加日程」**不需要离开聊天**，日程里立刻多一条，且这条日程的回执上写明「来自 与 XX 的聊天 · 10月30日 21:14」。

- **为什么现在做**：`apps/wechat/chat-view.js` 1006838 字节，是全仓最大文件，也是用户停留最久的地方。它当前是**纯看与回**——聊天里提到的每件事都要用户自己切 app 记下来。这是本仓「拟真」与「可用」之间最大的一道缝。
- **内核** `config/inline-action.js`（预算 ≤ 9K）：从消息文本提取候选动作（时间词 + 意向词），生成动作条目（`kind` + `payload` + `sourceMsgId`）。**只生成候选，不自动执行**——提交必须玩家点。
- **入口**：`chat-view.js` 里**新增旁路渲染**（按 P8 的施工约束：不改原函数体，只在消息渲染后追加一层动作条）。
- **撤销/降级**：动作条整体由一个开关控制，关掉后 `chat-view` 行为与今天**逐字一致**（有判据钉住）；某个动作执行后可撤销（复用 R13-O2 的 undo 分档）。
- **定向回归**：动作条出现**只在有候选时**（无候选的消息下方不许多出一块空白——那是本仓最典型的「看起来没坏但显示不对」）；提交后目标 app 里必须有条目且带 `sourceMsgId` 回源；负控制：把 `sourceMsgId` 去掉，判据须转红。
- **诚实边界**：提取质量**只保证「宁缺勿滥」**——本项把判据定在「误报率」上而不是「召回率」上：宁可少给动作条，不许给出错误动作。为什么这么定：动作条点下去会真写数据，误报的代价高于漏报。

### R13-X4 · 手机也会「不在手上」：离线与错过

**用户第一次能做什么**：把手机"放下"（一个显式开关，或按电量/时段自动），期间发生的消息、来电、通知**不推送**，但会记账；重新拿起手机时，有一个「不在的时候」清单：错过了什么、谁找过你、哪件事过期了。

- **为什么现在做**：实测 `offline|离线|missed` 命中 **60 个文件**，`battery|电量` 命中 **8 个文件**（含 `config/life-clock.js` / `config/device-face-bridge.js` / `config/system-notification-dispatcher.js`）——**基础设施全在，但没有一个「我不在」的产品面**。而「错过」恰恰是拟真手机最真实的一种体验：真手机不会让你 24 小时在线。
- **内核** `config/away-mode.js`（预算 ≤ 7K）：维护 `awaySince` / `awayUntil` / `missed: []`，提供 `markAway()` / `markBack()` / `missedDuring(from,to)`。**不拦截任何既有推送逻辑**——由各 app 的 dispatch 点主动查询 `isAway()` 决定是否静音，本内核只记账。
- **入口**：`apps/settings` 一个开关 + 回手机时的「不在的时候」页（可挂到消息 app 的顶部横幅）。
- **撤销/降级**：`isAway()` 默认恒 `false`，未接入的 app 行为零变化；整个功能可一键关闭。
- **定向回归**：`markAway` 期间派发的 N 条通知必须全部进 `missed` 且**一条都没真弹出**（两个方向都要证：记了账 / 没弹出）；`markBack` 后清单条数 = N；负控制：把某条的 `isAway()` 判定绕过，判据须抓到「该静音却弹了」。
- **诚实边界**：「过期了」如何判定（日程过了、消息太旧）**本项只给机制不给策略**——策略由各 app 自己提供 `isStale()`，本项只负责汇集。另外本项**不做**「回来之后自动补发通知」（那是另一种打扰）。

### R13-X5 · 同一件事，两种说法：谁看见了什么

**用户第一次能做什么**：同一条朋友圈/群公告，切到「别人眼里」看它长什么样——谁被屏蔽了、谁看不到、谁能看到但时间不同。**玩家能看见自己发的每条内容的可见范围**，且能改。

- **为什么现在做**：`apps/weibo` / `apps/wechat/moments-view.js`（132124 B）已有发布面，但可见性大概率是一层抽象（分不分组、屏蔽谁）。而「谁看见了」是社交产品里玩家最在意、最难验证的一件事。对照：记忆侧 `L13-X3` 在做「视角投影面」，两仓同构——但**各写各的**（那边投影的是记忆条目，这边投影的是社交动态）。
- **内核** `config/audience-projection.js`（预算 ≤ 6K）：输入 `{ contentId, audienceRules }`，输出「对每个角色而言，这条内容可见/不可见 + 原因」。**纯计算，零写面**。
- **入口**：朋友圈发布页的「谁能看到」预览；已发内容详情页的「视角」切换。
- **撤销/降级**：单纯叠加预览，不改既有可见性判定（既有判定仍是唯一真源）；预览与实际不符时以实际为准，并在预览上标注「预览基于当前规则，实际以发送时规则为准」。
- **定向回归**：屏蔽 A 后，A 视角下这条必须不可见且给出原因；未屏蔽的 B 视角下必须可见；负控制：把 A 从屏蔽名单删掉，A 视角必须立刻变可见（**双向**）。
- **诚实边界**：「角色自己会不会因为看不到而生气」这类**叙事后果不在本项射程**——本项只做可见性计算与预览，不生成任何角色反应文本。

### R13-X6 · 手机的「手感」：长时程的使用痕迹

**用户第一次能做什么**：手机用久了会有痕迹——某个 app 图标上多了一个自己加的小标记、某些通知被自己习惯性忽略、某个聊天变得很少打开。玩家能在「使用痕迹」里看见这些，并且能选择**承认**或**清掉**它们。

- **为什么现在做**：88 个 app 全部行为一致、干净如新，这对「拟真」是反的。真手机会留下使用痕迹。实测 `undo|撤销` 之外的「使用」类概念在本仓几乎为零——本仓有角色数据、有内容数据，**没有「我自己的使用数据」**。
- **内核** `config/usage-pattern.js`（预算 ≤ 8K）：记录每 app 的打开次数、最后打开时间、每次停留时长（只记聚合，不记内容）。提供 `trace(appId)` 四态读数（`never` / `rare` / `habitual` / `faded`）。
- **入口**：`apps/settings` 的「使用痕迹」分区；每个 app 详情页一行「你最近常/很少打开它」。
- **撤销/降级**：**默认不显示**（开关关），开启后才出现在界面上；数据只存本地聚合，可一键清零。
- **定向回归**：打开某 app 三次后 `trace` 必须从 `never` 变 `rare`；停用一段时间后变 `faded`（用注入的假时钟验证，不依赖真实时间流逝）；负控制：把聚合计数清零，`trace` 必须回 `never`。
- **诚实边界**：本项**只记录不解释**——不生成「你最近很少找我」这类角色台词（那需要模型，且容易变成廉价的情感绑架）。痕迹是给玩家看的，不是给角色用的。
- **隐私边界（本仓内部的）**：聚合数据落在本地 `PhoneStorage`，与角色数据**分开存放**，不参与任何导出/备份包（除非玩家显式勾选）。

### R13-X7 · 家务、账单、缴费：让"日常维护"成为可玩的一天

**用户第一次能做什么**：月底有一张「这个月要处理的」清单——房租、水电、订阅续费、体检预约——每条能直接在对应 app 里办掉，办完会留一条回执，没办的会过期并产生后果（房东催、断网、预约被占）。

- **为什么现在做**：`apps/accounting`（记账）与 `apps/affairs`（事务）都在，但没有「时间驱动的待办生命周期」。而这是拟真手机最容易被玩家记住的一层：**手机替人管着麻烦事**。
- **内核** `config/errand-lifecycle.js`（预算 ≤ 10K）：每条 errand 有 `{ id, dueAt, app, action, consequence, state }`，状态机 `pending → done | expired | waived`。**过期只产生一条「后果事件」，不自动扣钱**（扣钱必须玩家在场）。
- **入口**：主屏或 `apps/affairs` 的「这个月」页；每条 errand 的详情能跳到对应 app 办。
- **撤销/降级**：整个机制由一份 errand 表驱动，表为空时全线零行为；`consequence` 只生成**待玩家确认**的事件，不自动执行。
- **定向回归**：造一条 `dueAt` 已过的 errand，状态必须变 `expired` 且生成一条后果事件（**但不是已扣钱**）；办掉的必须 `done` 且留回执；负控制：把状态机改成自动 `done`，判据须转红。
- **诚实边界**：**「后果」的严重程度不在本项射程**——本项只给机制（过期 → 一条事件），具体后果（房东说什么、断网怎么表现）由各 app 自己写，且必须可回退。本项也**不做**自动扣款/自动续费这类不可逆动作，理由同 R13-O8：不可逆要单独设计。

### R13-X8 · 复述：让手机能讲出「我们之前聊过什么」

**用户第一次能做什么**：问手机「我们之前聊过搬家的事吗」，它给出一段**带出处**的复述：哪几条消息、哪一天、当时结论是什么——每条都能点回原位置。

- **为什么现在做**：这是本仓「记忆质量」这条主轴上最缺的一块。当前玩家要回忆，只能自己翻聊天记录。而本仓已有 `apps/memory/` 13 个文件、`apps/recall/` 3 个文件的底子。对照记忆侧 `L13-X1`（记忆沿革回放）——那边回放的是记忆条目的演化史，这边复述的是**聊天里的对话史**，形态不同。
- **内核** `config/recall-narrative.js`（预算 ≤ 11K）：输入一个主题，输出 `{ episodes: [{ at, msgs: [...], conclusion }] }`。**只用本地检索 + 规则归并**；若需模型总结，走宿主通道并标注「本轮用过模型」。
- **入口**：聊天页的「找找之前聊的」入口（或 `apps/recall` 的搜索框）。
- **撤销/降级**：纯读面，零写；总结失败时退回「按时间列出的原始消息」，并说明「没能归并，以下是原消息」。
- **定向回归**：每个 `episode` 的 `msgs` 必须全部是从真聊天里取得的真实 id（不许有幻觉 id）；点任一 id 必须能跳回；负控制：往 `msgs` 里塞一个不存在的 id，判据须转红（**这条是本期最关键的判据**——它守的是「复述不许编」）。
- **诚实边界**：归并质量（哪几条该算同一 episode）**不保证**；本项只保证「引用的每一条都真存在、可回源」。这也是记忆侧反复强调的那条：「宁可复述得笨，不许复述得假」。

### R13-X9 · 别人的手机：借来看一眼
> 已实现范围与取舍见[有源借看投影](../../implemented/feature/2026-11-03-other-side-phone.md)：不代表完整对方设备模拟已完成。

**用户第一次能做什么**：向某个角色「借手机看」，能看到**在他手机里**这条消息/这张照片是什么样子（他的通知栏、他的对话列表、他那边你的头像和备注名），看完即还，**不留痕迹**。

- **为什么现在做**：这是「拟真」的极限玩法，也是本仓独有的（其他产品不会做）。它同时回答了玩家一个很自然的问题：「我在他手机里叫什么名字」。前置：R6-X9 `parallel-life`（5676 B，零引用）做的是「另一条路线的手机」，与本项**不同**——本项是「同一个世界、另一个人的手机」。
- **内核** `config/other-side-view.js`（预算 ≤ 9K）：给定角色 id + 世界状态，渲染一个**只读**的他人手机视图片段（对话列表摘要 + 单条消息视角 + 对方的备注名/头像）。**严格只读、零写盘、零持久化**。
- **入口**：角色详情页的「借手机看看」（带显式的「看别人的手机」确认）。
- **撤销/降级**：关闭开关后入口消失；视图内**不提供任何操作按钮**（不许在别人的手机里发消息）。
- **定向回归**：视图内**零写面**（真源剥注释后不许出现 `setItem` / `save*` / `push` 等写词——沿用本仓既有的「零写面」判据范式）；显示对方给你的备注名必须来自真数据源，不是现编；退出后本机数据**逐字未变**（有判据比对退出前后快照）。
- **诚实边界**：这是本项**最大的伦理与技术双重边界**：① 它必然暴露「对方视角」的信息，某些信息（比如对方和别人的对话）**本项明确不做**——只给「与你相关」的那一屏；② 「他的手机界面」细节（他装了什么 app、他的桌面壁纸）本项**不生成**，只有你相关的那部分，否则等于凭空造一个没有真源的世界。这两条不是保守，是因为**造得越多越假**。

## 2. 九项的依赖与冲突矩阵

| 项 | 硬依赖（不做就做不了） | 软依赖（更好但可缺） | 与优化面的冲突点 |
|---|---|---|---|
| X1 一天 | **O4 时间单一源** | O6 空态分形（`absent` 态复用） | 无 |
| X2 模糊回忆 | 无 | O6 空态分形 | 与 `apps/search` 既有结果排序可能打架 ⇒ 只追加一栏，不动原排序 |
| X3 消息就地办 | O2 撤销分档（执行后要能退） | O8 回收站 | **`chat-view.js` 1MB**（P8）：必须走旁路渲染 |
| X4 离线与错过 | 无 | O9（通知面接线） | 与既有 notification dispatch 的关系是**查询**不是**拦截** |
| X5 谁看见了什么 | 无 | O4（"看到时间不同"需要时间源） | 零写面，与朋友圈发布逻辑无冲突 |
| X6 使用痕迹 | O4（时间聚合） | O5（痕迹也是设置面的一块） | 与 `apps/settings` 747560 字节的关系：**新增分区**，不改既有分组 |
| X7 日常维护 | O4（`dueAt` 判定） | O8（过期条目要能撤回） | **明确不做**自动扣款（与 O8「不可逆要单独设计」同一条） |
| X8 复述 | 无 | O4 | 纯读面，零冲突 |
| X9 别人的手机 | 无 | O2（"借手机"本身不可撤销，故不加 undo） | 零写面，但与「角色数据隐私」有观念冲突 ⇒ 见该项诚实边界 |

**三条读表就能看出来的结论**：

1. **O4（时间单一源）是整个拓展面的地基**——X1/X6/X7 三项硬依赖、X5/X8 两项软依赖。这不奇怪：九项里有六项都是「时间轴上的事」。所以交付顺序上 O4 必须先落，否则 X 面一半的判据都会因为「时间源不可靠」而写得含糊。
2. **两项动 `chat-view.js`（X3）与 `settings-app.js`（X6）**，都是巨兽文件（P8 / P6）。这两项的施工约束是「新增旁路 + 不动原函数体」，且都要有一条「关掉开关后行为逐字一致」的判据。
3. **X9 是唯一一项有伦理边界的**，其余八项都是纯功能性。它排最后，因为在争议未消之前不该让它占早期容量。

## 3. 交付顺序

```
先把地基（O4 时间源）
  └ 九项里六项在时间轴上，地基不稳则判据含糊
再做只读面（X2 → X8 → X1）
  └ 三件全是「让你看见已有的东西」，零写面，风险最低，也最容易验证
  └ X8 排第二是因为「复述不许编」这条判据（引用 id 必须真）是全期最强的一条判据范式
再做写面（X3 → X7 → X4）
  └ X3 动 chat-view（最贵），X7 动状态机（最容易写错），X4 动通知面
  └ 顺序按「误写代价」排：X3 写日程（可撤）< X7 写账（可撤但要二次确认）< X4 沉默通知（影响面最广）
再做观察面（X5 → X6）
  └ X5 可见性预览、X6 使用痕迹，两项都不改既有行为，纯叠加
  └ 排在写面之后，因为它们要投影的数据在写面落地后才有意义
最后争议项（X9）
  └ 单独一期评估，不与上面八项捆绑交付
```

## 4. Alternatives considered

| 方案 | 为什么不选 |
|---|---|
| 先把 R6 那 8 件孤儿接到界面上，当成本期拓展交差 | 那是**优化面 O3 的事**，不是拓展。拓展项必须是**新能力**，把旧孤儿接上不产生新能力，只是把「建了没用」变成「建了能看」。且 O3 已覆盖，重复占名额是浪费。 |
| 做「AI 主动给玩家发消息」这类情感驱动功能 | 那需要模型持续在场，且极易变成廉价的陪伴感。本仓纪律是「只记录不解释」（见 X6）——角色的话由角色卡负责，手机不该越界代言。 |
| X1「今天」做成主屏一大块全屏页 | 主屏格子已经 89 个 app 的压力很大。挂到 `apps/clock` 内部页签是更省的路径，也符合「时间是 clock 的主题」。 |
| X9 扩展成「能看对方的全部手机」 | 造得越多越假。对方和别人的对话、他的桌面壁纸、他装了什么 app——这些**没有真源**，全靠编，编出来的是另一个世界而不是同一个人。只做「与你相关的那一屏」是本项能守住的诚实上限。 |
| X8 复述直接用模型总结聊天记录 | 会幻觉出不存在的消息 id。本项把判据钉在「引用的每条必须真存在」上，这条比总结质量重要得多——所以先做本地检索归并，模型总结只作为可选上层。 |

## 5. Acceptance criteria

1. **九项全部有 app 内真入口**（无一项停在「内核已建」）——这是本期拓展的**第一验收条件**，源自 R6 的教训。
2. 九件新内核单件字节数 **≤ 12K**（超出必须拆）。
3. X8 的「引用 id 全部真实」判据必须有负控制（塞假 id 转红）。
4. X3 / X6 各有「开关关闭后既有行为逐字一致」的判据。
5. X9 的零写面判据（剥离注释后无写词）+ 退出前后快照逐字比对，两条都要在。
6. X4 的「记了账 + 没弹出」双向判据。
7. X5 的可见性双向判据（屏蔽即不可见 / 解除即可见）。
8. X7 的「过期只生成事件、不自动扣钱」判据。
9. X1 / X6 / X7 全部依赖 O4 已落地（时间源单一）。

**全期共同验收**：`npm run check` 全绿；`node --test tests/*.test.mjs` 只增不减；`dead-export-check` **无新增零消费导出**（这是本期拓展最容易踩的一条——新内核导出但视图没调用）；`method-consumption-audit` 的 `zero` 不新增；`dead-module-baseline.json` 不因本期新增 orchestrator-only 件。

## 6. Risks

| 风险 | 应对 |
|---|---|
| **最大风险：本期九项又变成九件孤儿** | 第一验收条件就是「有 app 内真入口」。且每项的内核预算压到 ≤ 12K，体积压力逼着把界面一起做完；另有一条硬判据：新 `config/*.js` 若 `productImporters` 为空即红（本仓 `dead-module-baseline` 已有这个能力）。 |
| X3 动到 `chat-view.js` 导致聊天流回归 | 旁路渲染 + 开关关闭判据 + 改动前 `wc -c` 记录基线，增量超出预期即停手。 |
| X7 的「后果事件」被写成不可逆动作 | 条目里已写死：不做自动扣款/自动续费。若实施时想加，必须单独立项（理由：不可逆动作要单独设计，同 O8）。 |
| X9 的伦理争议导致中途叫停 | 排最后 + 单独评估，不与前八项捆绑。若评估不通过，本期交付八项也算完成（验收条件里 X9 单列）。 |
| X2/X8 的检索在长聊天记录上变慢 | 本仓已有 `search_scale_baseline.json` / `reading_find_scale_baseline.json` 探针可复用，实施时必须先跑基线。 |
| 九项都想做导致周期过长 | 本份不排期，只排顺序。实施时每项独立成版、独立可弃——**任何一项可单独放弃而不影响其余八项**（这也是为什么依赖矩阵要写清：只有 O4 是硬依赖，X 面内部互不依赖）。 |

## 7. 本份自身的诚实边界

- 本份**全部读数为 2026-10-31 实测**（`v4.99.9 / e057a4d`）。P3 的 12 件模块字节数、`apps/` 引用数、`chat-view.js` 1006838 字节、`settings-app.js` 747560 字节、`offline|离线|missed` 命中 60 文件、`battery|电量` 命中 8 文件——均为当场 `wc` / `grep` 读数。
- **本份没有读过任何一个既有 app 的完整视图实现**（`chat-view.js` 1MB 未通读，`settings-app.js` 747560 字节未通读）。因此文中所有「既有逻辑大概率是……」（如 X5「可见性大概率是一层抽象」）都是**推断，不是实测**。实施前必须逐项核实，推断错则该项要重写。
- 本份**只制定计划**，不代表任何一项已实施或已升版。
- 本份**不承诺九项都能做成**。按 R6 的历史比例（9 成 1），做到 6 项已属超预期。所以依赖矩阵与交付顺序写得比常规更细——目的是让「中途放弃其中三项」变成一个有秩序的动作，而不是烂尾。
- 本份与记忆侧 `L13-X*` 的关系：**同词表、不同实现、不共享代码**。X2/X5/X8 与 L13 侧的 X3/X2/X1 在概念上同构，但两仓技术栈、数据形态、宿主完全不同，任何「抽公共库」的提议在本期一律不做——那会变成第三个仓库的第二套真源。


## X6 / X9 实施复核
X6 的旧侦察结论不成立：仓库已有 usage-tracker；当前复用采集口，设备本地存储与会话统计并存。详见[设备使用痕迹](../../implemented/feature/2026-11-03-device-usage-pattern.md)。逐 App 摘要在设置分区，未侵入每个 App 的原详情页。X9 缺少对方给玩家的备注等真实来源，本轮不实施，不用玩家给对方的备注冒充反向真源。
