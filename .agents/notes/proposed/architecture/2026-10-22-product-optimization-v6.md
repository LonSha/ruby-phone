# Agent Note: 第六期手机优化——从多个App到连续可玩的生活与创作

Status: proposed

## Problem

基线 v4.47.0 / `6184b21`，2026-10-22。本轮仅规划。现有任务入口、多目标草稿、群聊节奏、活动五步、话题演变、研究与续玩底座均不能再次申报为新功能。[证据页](../../../../docs/planning/2026-10-22-product-evidence-v6.md)记录源码范围与三项模块实跑，并纠正根计划“第五期全部待实施”的过时表述。

用户需要的是完整生活和创作体验，不是更大设置页。九项优化均需改变一段持续使用过程；加按钮、修守卫、调上限、重新包装已有入口不算交付。开创性指项目内机制跃迁，不宣称全球首创。

## Proposal

### R6-O1 · 以事情为中心的手机：一场活动贯穿消息、资料、日程与创作（P0 / XL）

- **现状与需求**：[R-E1/R-E4/R-E5](../../../../docs/planning/2026-10-22-product-evidence-v6.md#phone-evidence)。任务卡、通知聚合、LifeEventStore已存在；需要进一步让“筹备展览”成为持续工作的上下文，而非只是一排跳转链接。
- **机制与完整体验**：建立以事件引用为中心的进行中事务，保留当前阶段、参与者、待决选择、关联文档和动作结果。用户从群聊进入日历、查资料、生成海报稿后回到同一事务，能继续下一步而非重新解释来意。
- **增量边界**：不是再建桌面聚合页；新增跨App事务持续性、阶段转移和分工。仅持事务引用与交互状态，不复制源App正文。
- **落点/依赖**：`config/task-entry.js`、`config/life-events.js`、`config/open-ref.js`、`config/view-state.js`及现有 owner 动作；无本期硬前置，可单仓运行。
- **验收下限**：① 一次事务跨微信→日历→阅读→创作→微信完成且共享同一参与者/事件；② 中途关机重开恢复到未决选择，不重复执行已完成动作；③ 两件同名活动并行不串进度。320px和桌面均走真实点击全程。
- **代价/不做**：不接管各App存储，不用新的万能工作台取代全部界面；若只交付跳转卡则不达标。

### R6-O2 · 连续通信：消息、来电、错过与续谈形成同一段交流（P0 / XL）

- **现状与需求**：[R-E2/R-E3](../../../../docs/planning/2026-10-22-product-evidence-v6.md#phone-evidence)。已有聊天、来电归属、未读、主动调度和记忆注入。新目标是“正在沟通哪件事”跨媒介持续，而非又多一个未读徽标。
- **机制与完整体验**：按交流意图保存待回应问题、已说内容、约定续谈时机及渠道切换原因；文字转通话或错过后回拨沿用进度，不重问同一段。虚构角色忙碌、暂不回应与用户选择推迟都能进入后续互动。
- **增量边界**：不是重新实现主动消息、TTS/ASR或冷却时间；是跨通信渠道的议题生命周期。应用已读不自动代表角色理解，更不代表关系冷落。
- **落点/依赖**：`apps/wechat/`、`apps/phone/`、`config/call-attribution.js`、`config/global-social-store.js`、`config/phone-chat-memory.js`；依赖 R6-O1 引用机制，记忆 M6-X7只作可选语义增强。
- **验收下限**：① 文字约谈→错过来电→回拨时续谈同一问题；② 同一联系人两个议题保持独立；③ 用户关闭主动通信后不会借“续谈”绕过设置。真实宿主重开、换会话与生成连续三轮验证。
- **代价/不做**：仅虚拟手机内部通信，不发送真实短信/电话，不新增不可见后台模型调用。

### R6-O3 · 群聊议事与群像互动：角色有立场，议题有来回（P1 / XL）

- **现状与需求**：[R-E2](../../../../docs/planning/2026-10-22-product-evidence-v6.md#phone-evidence)。轮次冷却、@命中、沉默、投票及议题归属已有；完整群聊还需要观点承接、反提案、让步与未解决分歧。
- **机制与完整体验**：给议题维护各参与者提出/支持/保留/反对的内容和知情材料；发言围绕尚未回应的问题选择角色，可拆出分话题再回合并。投票只是一种收束，不强制多数意见抹平人物立场。
- **增量边界**：不是多加speakers或随机发言，不重做R5投票修复；新增多轮议事状态与人物互动结果。
- **落点/依赖**：`apps/wechat/group-scheduler.js`、`config/group-pace.js`、`config/group-vote-contract.js`与群聊生成链；可用现有角色资料独立运行，M6-X1可增强立场来源。
- **验收下限**：① 五人、两个议题、八轮对话后可回看谁提出什么、哪些问题未回应；② 新证据只影响知情人物的立场，不能全员同步读心；③ 一人退出、投票改期后仍能继续原议题。内容验收需确认角色真的承接对话，不只数据里有立场字段。
- **代价/不做**：不追求每轮全员发言，不启动五个无限自治代理。

### R6-O4 · 能改道的多人活动：计划遇到变化也能继续玩（P1 / XL）

- **现状与需求**：[R-E4](../../../../docs/planning/2026-10-22-product-evidence-v6.md#phone-evidence)。已有prepare→depart→arrive→interact→wrapUp、旅行协作、周期日程。新价值是活动中途遭遇变化时的协商与替代路线，不再每次从头建活动。
- **机制与完整体验**：把时间窗、参与者、地点、预算和分工连成可替换活动段；迟到、场所不可用、成员退出时提出局部改道方案，并向相关人发起确认。已完成段保留，未完成段重排，结束留下共同经历与分账结果。
- **增量边界**：不是给五步流程补按钮，也不重复多人空档查询；是可变计划的执行与再协商。距离/天气缺依据则让用户指定，不编造真实服务数据。
- **落点/依赖**：`config/date-playbook.js`、`config/recurrence-contract.js`、`apps/date/`、`apps/traveldesk/`、日历owner；依赖 R6-O1/O3，可消费 M6-O9但不必等它。
- **验收下限**：① 六人活动中两人迟到，保留已到场事实并协商新安排；② 改地点不重扣已支付费用，不把未到场写成亲历；③ 次日重开从新方案继续直到总结/分账。至少一次完整多App真人点击旅程。
- **代价/不做**：不做真实订票、付款和定位追踪；所有执行是虚构世界内的确认操作。

### R6-O5 · 长篇创作项目：从多份草稿升级为一部持续完成的作品（P0 / XL）

- **现状与需求**：[R-E5](../../../../docs/planning/2026-10-22-product-evidence-v6.md#phone-evidence)。八来源六目标、多目标独立文案、替图保文、版本比较与局部重做已在；不能把“多素材/多目标”再当新功能。
- **机制与完整体验**：以作品管理章节/场次、人物出场、素材依赖、创作意图与各平台发行形态；改动一个情节后由作者选择更新哪些章节/改编稿，保留未选章节的编辑。研究材料、配乐与插图围绕作品长期协作。
- **增量边界**：不是多加一个草稿列表；新增作品级结构、跨章节依赖和有选择的连带改稿。记忆插件维护事实材料，本仓维护作品编排与编辑成果。
- **落点/依赖**：`config/creation-multi-draft.js`、`config/creation-workbench.js`、`config/creation-pipeline.js`、`apps/creationdesk/`及目标App owner；依赖 R6-O1，M6-O6/O8可选增强。
- **验收下限**：① 三章作品各有图文/短帖改编，编辑第二章只更新用户选定的派生稿；② 断开记忆插件仍可编辑已保存作品；③ 重开、改源图、撤销局部改稿后人工文字不丢。作品须从素材选择到两个目标的虚拟发布全部跑通。
- **代价/不做**：不是再造云端协作编辑器，不宣称发布到真实互联网。

### R6-O6 · 主动研读工作室：从找句摘录到提出问题、比较观点、形成作品（P1 / XL）

- **现状与需求**：[R-E6](../../../../docs/planning/2026-10-22-product-evidence-v6.md#phone-evidence)。全书搜索、摘录、跨书专题与来源核对已有；新体验是围绕一个问题持续阅读，而非堆更多摘录卡片。
- **机制与完整体验**：把阅读进度连接到问题清单、观点对照、疑问批注与论证草稿；用户可把某段标为证据/反例/待核，随阅读展开专题结构。研究成果直接成为文章、人物考据或场景资料，不重复复制摘录全文。
- **增量边界**：不同于M6-O8的主张证据引擎，本仓负责并排研读、批注交互、阅读任务与写作组合；无插件时仍可手动建问题与观点对照。
- **落点/依赖**：`apps/reading/`、`config/reading-notes-contract.js`、`config/topic-dossier-contract.js`、`apps/creationdesk/`；依赖 R6-O5的作品结构，M6-O8仅增强自动查证。
- **验收下限**：① 从两本资料形成正反观点，均可跳回实际段落；② 半读中断重开后问题、批注与草稿一同恢复；③ 新版书替换后选择保留作者观点或重查，不覆盖正文。必须交付研读→成稿全过程，不以全文检索通过结项。
- **代价/不做**：不强制学习打卡、不自动替用户得出唯一正确理解。

### R6-O7 · 可重访的关系往事：回忆册从陈列页变成互动现场（P1 / XL）

- **现状与需求**：[R-E7](../../../../docs/planning/2026-10-22-product-evidence-v6.md#phone-evidence)。关系回忆册、共同往事选择、旧事重现与织信均已有。新能力是带着当下关系重访旧事，并在手机内产生新的交流。
- **机制与完整体验**：用户选择一段往事、讲述对象和分享范围；可翻旧消息、对照各自所见、发送询问或邀请重访。对方的回应形成新的交流记录，与旧事实分离；照片/音乐等可用素材围绕这一场回顾编排。
- **增量边界**：不是给关系卡加图片；M6-X8维护解释变化，本项交付邀请、对谈、分享和再次行动的互动体验，手动素材也可运行。
- **落点/依赖**：`config/relation-album-contract.js`、`config/shared-past-contract.js`、`apps/timeweaver/`、微信与创作入口；依赖 R6-O2/O5，记忆O7/X8可选增强。
- **验收下限**：① 一人愿意重谈、一人回避，后续交流不强制统一立场；② 私人旧消息可选引用范围，不整段泄露给其他角色；③ 重访活动产生新记录而非改写旧经历，重开后两者可分别阅读。至少三段不同关系阶段的交互内容验收。
- **代价/不做**：不默认所有往事都应分享，不自动和解或替用户发送。

### R6-O8 · 续玩再入场：从读简报升级为重新进入正在运转的故事（P1 / XL）

- **现状与需求**：[R-E8](../../../../docs/planning/2026-10-22-product-evidence-v6.md#phone-evidence)。跨项目续玩、分支对照、交接预检已存在；久未打开时，用户需要决定先回谁、先处理哪件事，而非再读一堆状态表。
- **机制与完整体验**：围绕上次离场点组织“现在可做的三条接续路线”，逐条带必要往事、未回消息与活动位置；用户选择回顾、补谈或直接进入一幕，手机恢复相应互动上下文。未选择的路线仍在原处，不自动推进世界。
- **增量边界**：不是再建项目列表或保存页面；新增可选择的再入场过程与情节/手机操作的连续接续，不把现实离线时长当剧情已流逝。
- **落点/依赖**：`config/resume-workbench.js`、`config/resume-brief.js`、`config/resume-handoff.js`及任务/通信/活动；依赖 R6-O1/O2/O4。
- **验收下限**：① 停在筹展中途重开，可选择补回群消息或继续准备，两条路径保留各自状态；② 切到另一项目不带入前项目材料；③ 用户选择不补看时不会伪造“角色已读所有消息”。完成断开重连、窄屏及真实生成的接续旅程。
- **代价/不做**：不以弹窗轰炸用户；不把摘要点击等同剧情确认。

### R6-O9 · 持续社媒生态：同一事件在不同圈层产生不同讨论与后续（P1 / XL）

- **现状与需求**：[R-E9](../../../../docs/planning/2026-10-22-product-evidence-v6.md#phone-evidence)。rootEventId话题页、转载/评论/辟谣、可知过滤已经实现。新价值是受众和讨论能持续演化，而不是一次生成数个外观不同的帖子。
- **机制与完整体验**：以圈层、角色关系、平台表达习惯和已见内容形成有界讨论阶段；观点可被回应、误读、澄清，后续草稿保留发展脉络。用户可以追踪同一话题从私人分享走向公开讨论，明确控制每次传播范围。
- **增量边界**：不是首次跨平台话题，也不靠帖子数量变多；新增受众差异与多轮互动后的议题演进。M6-X1维护人物解释，本仓负责发布/阅读/评论体验与虚拟传播。
- **落点/依赖**：`config/topic-echo.js`、`config/global-social-store.js`、`config/social-knowledge-bridge.js`和各社媒owner；依赖 R6-O1/O3/O5。
- **验收下限**：① 同一展览消息在三圈层产生不同且有依据的讨论；② 澄清只影响已看见的人，不全网瞬间同步；③ 私聊内容未经分享不进入公共话题，玩家关闭模拟后不继续自动发帖。多轮内容对照不能只统计帖数。
- **代价/不做**：只做虚构社媒，不做现实舆论操纵、营销自动化或外网批量发布。

## Delivery sequence

R6-O1先形成最小完整跨App事务；O2/O3与O5并行；O4/O6随后；O7/O8/O9在相应交流/创作能力上组合。每项独立交付一条完整旅程，不能先花数轮只建状态总线。双仓六批次见证据页。

## Alternatives considered

- **继续堆新App图标**：易展示，但用户仍要到处找入口；优先深化现有通信、活动、阅读和创作。
- **把全部状态集中到新“手机总数据库”**：跨页方便，但违反PhoneStorage/chatMetadata架构且复制owner；仅保存事务引用与本App拥有的交互状态。
- **直接把记忆插件的新数据画成卡片**：成本低，却是展示而非独立大更新；手机必须提供可操作的通信/协作/编辑闭环。

## Acceptance criteria

恰含R6-O1～O9九项。每项交付真实宿主点击、重开恢复、窄屏使用与生成内容结果；纯模块通过不能代替旅程验收。技术验证是这些功能的配套，不独立计项；无上游插件时可用范围与缺失增强必须可辨。按现行仓库纪律在整批收口执行全量门禁。

## Risks

最大风险是跨App流程拖成第二套平台。以现有owner、PhoneStorage及chatMetadata为唯一运行存储，不引入外部数据库；原文附件继续复用已有例外。限制主动生成预算与剧情时钟驱动范围，不用真实网络调用假装世界活着。每项若只有入口、配置或诊断完成，均不标交付。
