## O1 · 持久层 v3：每 App 声明、配额与越权写拦截

**缺什么**：`config/storage.js`（1748 行）已有 `STORAGE_SCHEMA_VERSION = 2` 与 `_migrationLedger` 迁移留痕 ——
但那是**全局一份版本号**。缺的是**每 App 一份声明**：101 个 App 各自 `JSON.parse` 后直接用，
字段增删靠 `||` 兜底。后果有三类，本仓历史上都真实发生过：① 旧会话里缺新字段 ⇒ 视图读到 `undefined` 后按默认值画，
用户看到的是**假数据**；② 字段改名后旧键变成孤儿，越积越多且没人报；③ 没有配额，单个 App 可以把会话元数据写到宿主拒绝写入。

**做什么**：
1. 在 `config/storage.js` 之上建 `phone-store.js`：每个 App 声明 `{schema, version, migrate(from,to), defaults}`；
2. 读写统一走 `store.read(appId)` / `store.write(appId, patch)`，**禁止** App 直接碰 `chatMetadata` 键；
3. 迁移失败必须**三态不同形**：`migrated` / `fresh`（旧键不存在，不是迁移成功）/ `corrupt`（读到但解析不了，保留原值不覆盖）；
4. 配额读数：每 App 当前字节数 + 会话总量 + 接近上限时的人话提示（不是静默失败）；
5. 孤儿键只登记不自动删（删除权在 O7 的体检面）。

**验收口径**：旧版 v4.157 会话包导入后，全部 App 的读数字段与新装一致（差异逐字段列出，不许「看起来一样」）；
坏 JSON 注入后读 `corrupt` 且原值仍在盘上；三个 App 各写 1MB 后总量提示可复现。

## O2 · 聊天渲染性能：兑现虚拟滚动与增量更新

**缺什么**：`chat-view.js` 18449 行、`renderMessage` 单次全量重绘；R21-O1 写的 60fps 虚拟滚动
**只留了注释与读数，渲染路径没改**。这一条在两期计划里被引用过三次，始终没落地。

**做什么**：
1. 消息列表改成**窗口化渲染**：只挂可视区 ±N 条 DOM，滚动时复用节点（不是内联 `innerHTML` 重铺）；
2. 新消息到达走**追加路径**，不触发整列表重建；历史插入（撤回/编辑）走**局部替换**；
3. 实测三档读数：200 / 1000 / 5000 条消息下的首帧时间、滚动帧率、内存占用，落成可复跑脚本；
4. 与 `chat-render-core.js` / `chat-call-core.js` 的边界不变，**只改挂载策略不改渲染产出**（DOM 结构对拍零差异）。

**验收口径**：DOM 快照对拍（现有 `chat_render_snapshot.json` 口径）在三种消息量下均零差异；
滚动帧率在 1000 条下不低于基线的 1.5 倍；`chat-view.js` 行数**只准降**。

## O3 · 启动优化：用现成读数换真收益

**缺什么**：两件「看起来该由本期做」的东西**其实已经做完了** ——
`config/boot-timing.js`（258 行）是启动耗时**读数层**（覆盖 78 个动态加载点、区分 `unmeasurable` 与「缺席」），
`config/app-lazy-routes.js`（110 行）把 67 段「import → new → render → catch」收敛成路由表（**代码**懒加载完成）。
但读数层自己的文件头写着：「**不是优化**，本版一条加载路径都不改」。
于是真实缺口是：① `phone.css` 717587 字节**整包合并**，101 个 App 的样式在启动时全进内存（**样式没有懒加载**）；
② 读数已经躺在那里，**却从未有一次「照读数改路径」的优化动作** —— 「没有读数的优化是把直觉当证据」，
反过来「有读数不做优化」也只是把证据供起来。

**做什么**：
1. 拆启动路径：桌面壳（图标墙 + 手势栈）先可交互，App 代码懒加载（已有分支，补齐**样式也懒加载**）；
2. `phone.css` 按 App 拆片 + 关键 CSS 内联首屏（玻璃拟态背景与图标墙），其余按需注入；
3. 建**启动预算读数**：冷启动可交互时间、首屏字节数、首帧 App 打开时间，三读数落台账并可复跑；
4. 量化前后对比，写清「哪一部分变快了、哪一部分没变」。

**验收口径**：桌面可交互时间相对 v4.157 基线下降（给出实测量，不许只写「更快」）；
样式懒加载后 Appearance 面（图标/圆角/阴影）逐像素对拍一致；离屏 App 未打开时不加载其 CSS。

## O4 · 主题包接线：让令牌真正生效

**缺什么**：`config/theme-pack.js`（187 行）**已经是完整的主题包内核** —— `THEME_PRESETS` 两套官方预设
（黑曜石钛极 / 极光浅柔）、自定义包、声明式安全导入（只允许有限 CSS 变量与白名单组件配置、禁止任意脚本求值）、
预览沙箱与一键回滚、会话隔离。
**内核在，接线没有**：全部 App 的色值是 `phone.css` 里硬写的字面量，**没有一处消费主题令牌**；
于是「换主题」改变的是设置对象里的字段，界面看起来没变 —— 这是本仓最贵的缺陷形态「不报错、不崩溃、只错表现」。

**做什么**：
1. 抽出 `config/theme-tokens.js`：语义令牌（`surface` / `onSurface` / `accent` / `divider` / `glass`）与外观令牌分离；
2. 每 App 主色登记为**数据**（沿用 `config/apps.js` 的 `color`），由令牌层派生 hover / pressed / 弱化三档；
3. 明暗双模（深色为默认，保持现有观感**逐像素不变**），切换走设置页并在会话内持久；
4. 自定义主题：用户改令牌值即可换肤，不要求写 CSS；导出/导入主题包（纯 JSON）。

**验收口径**：默认深色下与 v4.157 截图逐像素对拍零差异（这条是硬门槛，防止「换主题把原样换没了」）；
亮色模式下**每个 App 的文字对比度**达到 4.5:1（可计算，不许目测）；主题包往返导入导出字节等价。

## O5 · 图片与媒体内存治理

**缺什么**：相册、头像、头像框、贴纸、PV 封面等面都存在图片，但仓库里没有统一的**图片生命周期**：
谁缓存、缓存多少、什么时候释放、缩略图怎么生成，各 App 各写一套（或干脆不写）。

**做什么**：
1. `config/media-cache.js`：LRU + 字节上限 + 会话级释放（挂 `onChatChanged` 与 `releasePhoneInactiveResources`）；
2. 缩略图策略：列表面只取缩略，详情面才取原图；缩略尺寸按显示尺寸 × dpr 计算并登记；
3. 失败三态：`loaded` / `failed`（有错误码）/ `absent`（**没有这张图**，不是加载失败）；
4. 读数：当前缓存字节、命中率、被释放次数，暴露到「洞察」App 的一个分页。

**验收口径**：连续打开 30 个含图的 App 后缓存不超过上限且不 OOM；
同一图片第二次打开走缓存（命中率读数可复现）；缺图与加载失败在界面上**不同形**。

## O6 · 设置中心信息架构重构

**缺什么**：`settings-app.js` 12362 行、104 个方法，`bindEvents` 5374 行、`render` 2308 行，
是全仓第二大的单文件，也是用户唯一必进的 App。R23 只做了「方法体内切片」的方法学（切了 2 段，-82 行），
**信息架构一次没动**：所有设置平铺，找一项要滚很久。

**做什么**：
1. 按**用户任务**重组分组（我 / 角色 / 生成 / 手机外观 / 数据 / 高级），每组一屏内可扫完；
2. 设置项**登记制**：每项声明 `{id, group, label, default, effect}`，渲染由登记表驱动，不再逐个手写 DOM；
3. 搜索沿用 `config/settings-filter.js#filterSettings`（唯一实现，不新建第二套）；
4. 每项带「这项改了什么」的一句话说明（写入登记表，界面直接显示，不另写文案）。

**验收口径**：全部现有设置项**一项不少**（登记表条数 = 现有可交互控件数，差异逐条列出）；
搜索命中与旧实现同结果（同一查询集合对拍）；`bindEvents` 事件挂载序列对拍不变。

## O7 · 数据体检与自愈面（用户可见）

**缺什么**：仓库有诊断 App（`apps/diagnose`），但它读的是**上游桥归因**，不是用户数据本身。
用户数据层面的问题（孤儿键、超大 App、坏 JSON、指向不存在的引用）**没有任何面能看见**，
更没有「修」的动作。

**做什么**：
1. 体检项：孤儿键 / 超配额 App / 坏 JSON / 悬空引用（如消息指向不存在的联系人）/ 重复记录；
2. 每项给出**人话结论 + 影响面 + 可执行动作**（清理 / 合并 / 保留），动作前先算「会删掉多少、保留什么」；
3. 只读模式先出报告，用户点确认才写；写入走 O1 的 store，**不绕过迁移层**；
4. 体检结果可导出为一页文本（用户能贴给开发者）。

**验收口径**：构造 5 类脏数据样本，体检全部识别且**互不误报**（每类单独出现时只报该类）；
清理动作执行后再次体检为干净，且「被保留的数据」逐条可查；只读模式不产生任何写盘。

## O8 · 无障碍 v2：键盘与焦点

**缺什么**：R22-O3 补齐了 `aria-label`（基线 350/115/17），但**键盘可达性**没有：
图标墙、抽屉、弹窗、列表项的焦点顺序与焦点陷阱都没定义，键盘用户进得去出不来。

**做什么**：
1. 焦点模型：图标墙 → App 内 → 抽屉/弹窗 三层，每层一个 `focusScope`；
2. 弹窗焦点陷阱（Tab 循环、Esc 关闭、关闭后焦点回到触发元素）；
3. 快捷键：桌面方向键移动、Enter 打开、Esc 返回（与物理手势并存，不冲突）；
4. 焦点可见样式走主题令牌（O4），**不许**用 `outline: none` 抹掉。

**验收口径**：纯键盘完成「打开微信 → 发一条消息 → 返回桌面」全链路（脚本化按键序列可复跑）；
弹窗打开时 Tab 不出界；关闭后焦点回到原按钮（断言 `document.activeElement`）。

## O9 · 巨型数据文件治理：`cheats.js` 数据/代码分离

**缺什么**：`data/cheats.js` **27611 行**，是全仓最大文件，也是 R23-O8 明确登记为「未开工」的唯一一项。
它是**数据**（万界武库条目）却以 JS 模块形式整包进内存，导致首屏与包体双重负担。

**做什么**：
1. 数据迁到 `data/cheats.json`（或分片 JSON），代码只留**查询与投影**；
2. 按需加载：打开「金手指」App 时才取，取回后分页渲染（与 O2 的窗口化同口径）；
3. 判定用**调用链**证明真加载：从 App 打开到首条渲染的路径逐跳可查，不许只写 `import` 就算；
4. 顺带核 `gacha-items.js`（11926 行）同族问题，同批处理或明确留到下期（不静默跳过）。

**验收口径**：`cheats.js` 物理行数降到千行以内；金手指 App 全功能可用（条目数、检索、装配、生效逐条对拍）；
未打开该 App 时该数据不在内存（读数证明，非字符串断言）。
