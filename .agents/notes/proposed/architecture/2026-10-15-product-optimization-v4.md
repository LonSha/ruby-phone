# Agent Note: RubyPhone 第四期优化提升九项——把已有能力变成好用的手机

Status: proposed

## Problem

2026-10-15 基线：`main@fe5f04f`，v4.12.0；侦察开始时工作区干净，fetch 后与 origin/main 同步。本轮只制定计划，不实现功能、不抬版本。

第三期 R3-O1～O9 / R3-X1～X9 已有实现与专属测试，不能照抄旧缺口。另一方面，纯函数能给出恢复读数，不等于页面真的恢复；出处字段存在，不等于用户点得开。新的优化名额必须对应具体用户操作，不能继续兑换成诊断出口、守卫数量或版本台账。

证据等级：**实测**指本轮直接执行现有纯函数；**读码**指实现与调用点核对；**待体验**指需真实宿主、浏览器或模型验证。本轮没有执行新一轮浏览器体验测试。以下标注的性能数值均为拟验收目标，不是现有成绩。

## Proposal

采用 R4 新编号，保留旧计划的实现历史；九项全部为待实施提案。P0 优先保住内容和用户操作，P1 改善高频使用。M/L 表示中型/跨模块工作量，不承诺工期。

### R4-O1 · 往事答案真正可点开出处（P0 / M）**已完成**,v4.13.0
- **现状证据｜读码**：`apps/memory/memory-view.js::_askFaceHtml` 把 ledger/floor 渲染为普通 div；注释说“可点开”，实际答案行没有跳转按钮。`config/memory-qa-contract.js::qaRefOf`、`config/open-ref.js` 已提供引用基础。
- **用户收益与增量**：从“相信一行摘要”变成“点开原文核对”；答案显示友好出处、命中句和前后文，返回后保留问题与结果。
- **落点与依赖**：memory App + open-ref，复用来源 owner；不等上游新问答算法即可先做。源缺失、换代、受限分别提示，不按当前同楼文本冒充旧来源。
- **验收**：在真宿主逐一点击有效楼、0楼、删楼后的失效引用、受限引用；有效项定位对应原文，失效项不误跳；往返两次问题、筛选和滚动保持。
- **不做**：不复制原始聊天、不新增来源台账、不把账本缩写当唯一用户文案。

### R4-O2 · 问答与检索可取消、可继续操作（P1 / L）**已完成**,v4.14.0
- **现状证据｜读码**：`memory-app.js::askPast` → `readMemoryQaAnswer` → 上游同步 `askMemoryQuestion`；上游虽已有 `evidence-query.js::queryAsync`，当前这条按钮链仍是同步调用。全局搜索已有让出与取消，不能再宣称整个手机没有取消机制。
- **用户收益与增量**：大库搜索时仍可输入、返回、换会话；快速连续提问只展示最新一次结果。
- **落点与依赖**：复用搜索的请求身份/取消做法；接 M4-O4 的异步查询能力，保留旧插件的明确兼容路径。加载、部分结果、取消、真正空结果各有用户文案。
- **验收**：2万条证据样本上连续提交3次、取消、切聊；旧请求不覆盖新问题，取消在下一协作分片生效；真浏览器记录最长主线程阻塞与输入响应，改善必须有同设备前后对照。
- **不做**：不新增后台检索服务或性能监控平台；Node 耗时不冒充手机流畅度。

### R4-O3 · 跨 App 返回恢复实际页面状态（P1 / L）**已完成**,v4.15.0
- **现状证据｜读码**：`config/desk-focus.js::restorePlan` 是比较器；`apps/taskentry/taskentry-app.js::markLeft/restoreReading` 明写“不做恢复动作”。页面栈已存在，不能把“新建返回栈”再列一次。
- **用户收益与增量**：搜索→详情→聊天→返回后继续原任务；本轮做真正的状态捕获和恢复，而不是再增加恢复成功读数。
- **落点与依赖**：现有 PhoneShell 页面栈、search/memory/creationdesk/reading 四个高频入口；保存页签、查询、定位锚点，按会话隔离。与 R4-O5 共用已有草稿 owner，不把正文塞路由状态。
- **验收**：四条旅程分别用按钮、滑动、浏览器返回往返；原查询和选中项不丢，滚动恢复到同条目；切到另一会话不恢复旧会话状态。先修测出的具体缺口，已有正确路径不重写。
- **不做**：不造第二路由、不要求所有低频 App 一次重构。

### R4-O4 · 长聊天按窗口呈现，不重铺整段记录（P1 / L）**已完成**,v4.16.0
- **现状证据｜读码**：`apps/wechat/chat-view.js::renderMessagesWithDateDividers` 遍历传入消息数组，多条刷新路径整体替换 messagesDiv；已有增量追加和滚动补偿，但未形成统一可视窗口。`config/list-window.js` 已服务社媒，R3-O5 不是本项的重新交付。
- **用户收益与增量**：几千条聊天仍能回看、引用、定位旧消息；新回复不把正在阅读旧记录的人拉到底部。
- **落点与依赖**：复用 list-window 思路和稳定消息 ID，适配日期分隔、图片高度变化、群聊、引用跳转；实现前逐条核对上游是否已切片，避免双重裁剪漏消息。
- **验收**：5000条含图片/语音/日期分隔的会话，拟定同时渲染不超过300条消息；跳到第20条再返回最新，引用与时间分隔正确；真浏览器测滚动，不用数组长度证明流畅。
- **不做**：不删历史、不压缩用户消息、不以关闭核心气泡功能换性能。

### R4-O5 · 未点保存的编辑内容也能恢复（P0 / M）**已完成**,v4.17.0
- **现状证据｜读码**：`creationdesk-app.js::setDraftNote` 只更新 `_draftNote`，input 监听调用它，保存走另一个 `draftAct`；切聊会清实例字段。`workflow-design.js` 的编辑草稿同样为实例态。已有草稿本只保证已保存版本。
- **用户收益与增量**：打了一半的文案、流程参数不因离开页面或刷新丢失；区分“正在编辑”“已保存”“已发布”。
- **落点与依赖**：复用 creation-multi-draft 与 workflow 模板 owner，增加会话级编辑缓冲/防抖持久化与恢复选择；关闭、切聊前及时冲刷，已发布内容不能被恢复缓冲反向覆盖。
- **验收**：输入但不点保存，离开/重开/刷新均可恢复；A→B→A 不串稿；保存失败显示未保存并保留文字；恢复旧缓冲需选择，不自动覆盖新版本。
- **不做**：不再次造多目标草稿系统，不自动发布，不长期保存输入框里的密钥。

### R4-O6 · 超长章节阅读与精确进度恢复（P1 / M）**已完成**,v4.18.0
- **现状证据｜读码**：`reading-view.js::_renderReader` 对整章 paragraphs.map；进度展示主要按章节比例。正文 IndexedDB 附件与摘录已实现，不再把“正文落盘”列为新功能。
- **用户收益与增量**：无分章大 TXT 不一次塞满 DOM；字号/主题变化、摘录回跳后保持同一段落位置。
- **落点与依赖**：reading App 的段落窗口、段落 ID 与偏移锚点；复用本地附件及既有进度字段，先支持平铺长章再处理 EPUB 复杂排版。
- **验收**：单章2万段文本，拟定可视邻域不超过250段；首/中/末三处刷新、改字号、摘录回跳均回到同段，所有段可读且复制不丢字；真浏览器测首屏和滚动。
- **不做**：不以截掉长章代替分页，不引入在线书库或新数据库服务。

### R4-O7 · 通知按事情收拢，而不只是按发送者覆盖（P1 / M）**已完成**,v4.19.0
- **现状证据｜读码**：`config/system-notifications.js` 有200条历史、按 senderKey 三分钟合并；控制中心已有全局免打扰。缺口是同一发送者的不同事件与同一事件的多次更新缺少面向用户的整理方式。
- **用户收益与增量**：同一约会的改期聚为一组，另一笔转账不被并掉；按 App/联系人静音、稍后看，保留重要约定提醒。
- **落点与依赖**：扩展 NotificationLog 现有记录的事件引用与呈现策略，复用 action-center；提醒仍用现有调度，静音只影响打断不删消息。
- **验收**：同发送者两事件、跨 App 同事件、重复提醒三组实测；未读与详情对应，静音后历史仍在，点击直达正确对象。缺事件 ID 时保守分开。
- **不做**：不重造通知中心，不开启后台 LLM 归类，不许把未读数下降当体验改善证据。

### R4-O8 · 流程编排用对象选择器而不是内部键名（P1 / M）**已完成**,v4.20.0
- **现状证据｜读码**：`apps/workflow/workflow-design.js` 直接显示 `st.paramKeys/st.faces`，参数用通用文本框；动作、顺序、条件和保存模板已可用，不能再提“可视化编排从零建设”。
- **用户收益与增量**：选联系人、日期、草稿和结算对象即可排流程；在运行前看见“会替谁做什么”，不需要猜内部 ID。
- **落点与依赖**：复用 WD_ACTIONS 五种白名单及现有运行器，给既有参数补中文名称、类型控件、对象预览和缺项定位。编辑中断恢复由 R4-O5 负责。
- **验收**：不输入任何内部 ID，完成“整理记录→存草稿→提醒”和“结算→日历”两条流程；已删除对象明确要求重新选择；写步骤仍逐项确认，拒绝不执行。
- **不做**：不增加任意 JS 节点、不造插件市场、不扩大动作表来掩盖当前难用。

### R4-O9 · 本地附件随备份真正搬走（P0 / L）**已完成**,v4.21.0
- **现状证据｜读码**：`reading-attachment.js` 已用 IndexedDB 存正文并明确元数据不等于附件；`config/data-backup.js` 的备份模型围绕 storage 键，未见阅读正文附件消费。实现前进一步核对宿主导出入口，不能凭“备份成功”认定书籍已打包。
- **用户收益与增量**：换浏览器/设备后书架不剩空壳；导出前能看清正文、图片引用和未包含远端资源。
- **落点与依赖**：复用 backupdesk + data-backup + 本地附件 owner；选范围→估算体积→导出正文包/附件包→预览导入。保留现行零数据库架构及已批准本地附件例外，不加服务器。
- **验收**：在空存储环境恢复一本 TXT、一本 EPUB 及摘录/进度，离线可读且正文 hash 相同；中断/配额不足不报完整恢复；重复导入不产生双书，删除附件前列清引用它的书架项。
- **不做**：不静默下载外链图片、不上传云端、不把“完整手机备份”用于仅含元数据的包。

## 执行顺序与取舍

第一包“内容不丢”：O1/O5/O9；第二包“用起来顺”：O2/O3/O4/O6；第三包“减少操作负担”：O7/O8。可以并行独立项，但每包必须交付可实际操作的旅程，不将三包拆成守卫扩建版本。

与[拓展九项](../../proposed/feature/2026-10-15-product-expansion-v4.md)互补：本篇只改善已有操作，拓展篇增加新的用户工作流。跨仓记忆事实仍归 lonsha-memory-plugin；手机只保存自身 UI 状态、草稿和引用。

## 第五期接续说明（2026-10-20）

本篇保留第四期的理由、版本与验证边界；后续排序由[第五期O九项](2026-10-20-product-optimization-v5.md)接管。两篇部分重叠而非完全替代：已有模块继续复用，第五期按具体语义/真实消费缺口补闭环，并明确区分新能力；不得将本篇历史“当前缺口”直接复活成从零任务。

## Alternatives considered

- **继续扩守卫**：能快速增加可量化读数，但无法让用户点开出处或找回文字，否决作为独立计划项；只保留与改动直接相关的回归。
- **重写手机架构**：能统一接口，但会牵动大量已用 App；选择先打通高频旅程，不按文件体积重构。
- **照旧勾选继续执行第三期**：最省规划成本，却会重复建设；改用新编号并明确每项与已有实现的差量。

## Acceptance criteria

每项分别记录“代码/自动化已实现”“真宿主操作已验”“真实模型效果已验或不适用”，不能用前者替代后两者。浏览器验证进入该功能自身验收，不单开“实机守卫”产品项。产品验收以前述用户动作完成为准，不以新增测试数量为成果。

本轮计划验收为：九个唯一 O 编号、九个对应 X 编号、所有源路径可定位、既有能力不重复列入、依赖可排序、两仓提交推送。功能实施期间按 AGENTS.md 定向验证，收口按仓库要求一次全量；不新增计划管理服务或常驻审计。

## Risks

本轮读码并不证明每条旅程都已在手机复现；涉及恢复/性能的项须先在真实入口核对再改。附件的本地配额、宿主 CSP 与移动端后台行为有环境差异。若接口升级被阻塞，明确显示不可用，不把本地假数据当上游结果。计划不预先授权任何用户数据迁移、外网发布或云端同步。
