# Agent Note: 通话同名人工认领(R3-O1 消费侧闭环)
Status: implemented
## Problem
计划原文要的是「接待、群发言、@、短信/通话统计用稳定角色与联系人 ID;别名仅用于候选查找,歧义提示选择并保留绑定;历史记录无 ID 时不猜」。修前实测三处缺口(不是推演):
1 **内核侧**:contact-insight.js 读通话时只读 call.name 与 call.contactName,而 PhoneCallView._addCallRecord 写入的真实字段是 **caller** —— 每一条生产通话都被静默跳过,界面读数恒为「这个人从没打过电话」:不报错、不崩溃、只错读数,且既有判据全部用 name 字段的合成输入,所以长期全绿。
2 **消费侧**:内核虽已支持 callAttribution 参数与 unattributedCalls 输出,但 collectContactInsight 只传 staleDays,认领账**全库零消费**,界面无候选、无认领、无撤销 —— 内核能力悬空。
3 **生产侧**:新通话记录不写 contactId,能自动归属的那些也一律只能靠人认领。
另有一处**声明与真码脱节**:内核那段注释自己写着优先级是「一 有 contactId 按 id 精确归属;二 有认领按认领……」,而真码是 claimedRow 排在 target 前面 —— 有 contactId 的通话会被姓名级认领**从正确那一行挪到别处**。
## Decision
新内核 `config/call-attribution.js` 是会话级认领账的唯一实现,三条纪律:一 **不猜**(空名、空 ID、纯空白一律如实拒绝且**不落任何键**);二 **可撤销**(撤销即删键,没认领过时如实返回 false 而不报错不补写);三 **不抛**(读抛异常或存储里是坏 JSON,一律按「没有任何显式认领」处置)。归一出口只认「非空名到非空 ID」的纯对象,数组与字符串按畸形丢弃。
**键归属**:新键 `phone_call_attribution` 靠既有前缀 `/^phone_call_/` 落在 chatMetadata,已按 K1 登记为 chat 作用域;换会话与清数据两条路径随既有机制一并生效。本版**不新增 App、不新增路由、不改全局设置面**。
**接线三层**:一 取数层 apps/usage/usage-data.js 的 collectContactInsight 增第三参 storage,读出认领账并传入内核(第三参可选,既有调用点不破);二 控制器 apps/usage/usage-app.js 新增 callAttribution 读出口与 claimCall、unclaimCall 两个写出口,**写成功后立即现取**洞察;三 视图 apps/usage/usage-view.js 的联系人页新增「未归属通话」卡,候选一律来自内核 candidateIds,**视图不重算**。
**归属优先级**按注释声明的顺序落实:记录自身 contactId 精确匹配优先,其次显式认领,最后唯一姓名匹配;同名多候选且无稳定 ID 与认领时进入 unattributedCalls,不计入任何联系人,也**不默认选第一人**。
**新通话记录补稳定 ID**:PhoneCallView._addCallRecord 经既有 _resolveWechatContact 解析微信联系人并写入 contactId;拿不到写空串,**绝不**按姓名猜、也**不**用电话联系人本地 ID 冒充微信 ID。
## Alternatives considered
- **在联系人洞察里按姓名自动归属第一个候选**:最省事,但正是计划原文禁的那一步(「歧义不猜」)。同名两人在现实里就是两个人,静默算给第一个会让通话读数**长期错给某人**且无人发现。故宁可显示「未归属」也不猜。
- **认领账写全局设置而不是会话**:跨会话复用看着方便,但「这个会话里这个名字是谁」是**会话内判断**;写入全局会让 A 会话的认领污染 B 会话的同名角色。故靠既有 /^phone_call_/ 前缀落在 chatMetadata。
- **用电话联系人本地 ID 充当微信联系人 ID**:两者都叫「联系人」,看着可互换。但电话本地簿与微信通讯录是两套独立台账,混用会让「按 id 精确归属」变成跨表撞号。故解析不到微信侧就如实写空串。
- **认领后台只靠下一次页面重建生效**:实现更简单,但用户点完按钮看不到任何变化 —— 本仓第二类形态的典型。故写成「写成功后立即现取」。
## Consequences
四件随本版面变的东西逐项对账,全部由现场取数写入,零手抄:`docs/runtime-verification-boundary.md` 的语法面 795 → **797** 文件、导入面 452 → **453** 文件 / 790 → **792** 条(新增 config/call-attribution.js 与 tests/system-v4110.test.mjs 两件);四张取证基线的枚举面读数 +1;状态台账当版置 4.11.0。
## Testing
定向套件 `tests/system-v4110.test.mjs` 二十例:A 口径四例(键归属真在前缀面而非注释里 / 归一形态 / 四个出口各有真消费点 / 零宿主边界);B 行为七例(空值如实拒绝且不落键 / 认领生效加撤销恢复未归属加幂等 / 读不抛且坏 JSON 按空账 / 生产通话必须被统计 / 认领后计入该行且不连带 / contactId 优先于认领 / 取数层真把账传下去);C 接线四例(视图卡与按钮且事件真的被绑定 / 样式两侧投递 / 控制器写后现取 / 电话记录写 contactId 且不冒充 / 键登记与清理路径);D 负控制四例(阳性对照加三条真源码定点破坏:caller 字段、空值拒绝、撤销删键,每条都配原版上同款判据必真的反向对照);E 版本锚一例(下限形)。
## Verification boundary
本版在无头环境验证的是认领账内核行为(拒绝与撤销与不抛与归一)、内核归属优先级三态(caller 归属与 contactId 优先与未归属)、取数层真传账、以及按真源码文本核对的接线与样式投递。**未做**真实宿主下「在手机上点候选按钮之后那张卡是否真的变了、撤销之后那一行是否真的回到未归属」——那需要在真机浏览器里走一遍旅程。另:未归属通话卡只在**同名多候选**时出现(唯一姓名匹配会直接归属),故单角色会话看不到这张卡,这是设计而非缺陷。

## 抬版过程中自己抓到的坑(如实留痕)
**一 收尾条括号写成了半角 —— 这是本仓第五次踩同一个坑。** 段里的 `【版本升至 4.11.0(五源同源)】` 括号误用半角,而仓内历史所有版本用的是全角 U+FF08 / U+FF09。后果不是文案不好看:v285 / v286 / v287 / v3960 四档的「版本升至 X(五源同源)」判据全红(它们把括号当正则分组符,匹配不到全角原文)。抬版落盘后由全量门当场抓回;修法不是改判据,而是用 `chr(0x28)` / `chr(0xff08)` 明写字节做替换并把校验写成「该行不得出现半角括号」。前四次同坑已在 v4.10.0 迭代段登记,本版是第五次。
**二 多行 heredoc 传 Python 会被 bash 拆坏。** 本版派生 tools/bump_v4110.py 与 tools/refresh_baselines_v4110.py 时,多行 `<<PY` 脚本被交互层按提示符逐行重排,出现 `unterminated string literal` —— 而同一脚本改写为单行 `python3 -c` 后一次通过。故本版批量锚点改写一律走单行 -c,并把每次替换写成**先断言计数命中恰为 1 次、再替换**。
**三 裸 `git log` 会把终端会话挂住。** 它唤起分页器后会话失去响应(`echo alive` 都不返回),后续所有命令超时;退出分页器(q)后会话恢复。故本仓后续 git 命令一律带 `--no-pager` 或 `GIT_PAGER=cat`。
**四 回滚五源重抬版是幂等的。** 本版因段修订重抬了三次,每次都是 `git checkout --` 六份版本面文件后重跑 `tools/bump_v4110.py --write`,三次全量门结论一致 —— 抬版脚本的「dry-run + 逐份断言 + 只写五处」纪律让重跑无副作用,这正是它值得被抄来抄去的原因。
