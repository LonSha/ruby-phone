# Agent Note: R14-X3 条件提醒的来源与通知恢复

Status: implemented


## Problem

工作流具备显式动作入口，但没有用户可编辑的等待条件，也没有条件满足到通知落账的恢复协议。

## Decision

条件提醒使用会话键 wf_condition_reminders_v1，事务台这个月和日历提供入口。任务完成从共同事项 owner 的操作回执读取；指定发送人的有效文字回复从微信 addMessage 成功收存后匹配。条件仅接受创建后事件，禁用不触发，回执存在不重复匹配。任务事件时间是操作记录时间，回复沿用消息保存的 realTimestamp；不替换消息剧情时间。可限定聊天 ID，留空明确表示匹配所有聊天。

匹配先写来源回执，再提交通知，再写通知 ID 并回读核验，静默写失败返回失败供重试。中断恢复按稳定 senderKey 查找既有通知；来源 ID 同时出现在提醒页和通知文字中。没有后台定时器、常驻模型或新增生命周期监听。

地点图景上游提供到访聚合与楼层，没有已核验的独立事件身份和操作时刻；该条件明确暂不可用，不将计数变化编造成事件。

## Alternatives considered

轮询所有微信历史消息能避免改 owner，但剧情时间不能与提醒创建的操作时间比较，而且会误报旧消息，因此采用成功接收后的 owner 调用。后台定时器能定期检查，但增加关闭与换会话生命周期成本，采用 owner 变更和页面读取时检查。

## Consequences

匹配、通知恢复与旧消息重放有九项定向测试。Chromium 131 存储夹具页面场景五条读数通过，覆盖创建、回复幂等、来源显示、禁用与缺源提示。键登记和死导出审计通过。真实 SillyTavern 宿主端到端未执行；sender 按微信实际保存名称精确匹配，不声称跨重名身份解析。通知提交后调用既有 flushNow；底层异步存储的崩溃原子性仍受既有 owner 保证范围限制。
