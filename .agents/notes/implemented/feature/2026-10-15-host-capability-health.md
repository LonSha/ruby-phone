# Agent Note: 宿主与能力健康中心

Status: implemented

## Problem

v3.92.0 之前，本仓有八十六个 App、十几个上游契约、两条桥、三种生图通道、两端语音，但**没有一处**能回答「这台机器此刻到底有什么能力」。修前实测四条后果：

① **能力缺失与读数缺席长得一样**：搜索 App 没加载过、记忆桥没挂、生图没选通道，界面给的都是一片空白；② **接口在场被当成服务可用**：桥挂上了就画成「记忆可用」，而桥挂上到真产出快照之间隔着好几轮；③ **缺能力不给替代路径**：一项不可用时，用户只拿到「不可用」三个字，没有「那还能怎么办」；④ **双项目版本不一致零提示**：记忆插件版本偏低配手机端的最新生图协议会静默少功能，界面上没有一句话。

宿主版本的处境更极端：`grep -rn 'version_display'` 与 `SillyTavern.version` 双双零命中 —— 全仓**没有一处**读过宿主版本。

## Decision

判定内核 `config/capability-health.js` 是四态判定、六项能力登记、替代操作表、汇总面、跨仓提示、诊断报告、自检的**唯一实现**。它**零 import 之外的依赖、零 IO**：不读时钟、不读存储、不联网、不碰 DOM，观测与版本全由调用方注入。

四条口径决定了这个模块的形状：

- **四态刻意不同形**（可用 / 部分可用 / 不可用 / **未验证**）。压平任何两态都会造出「两种处置相反的处境长得一模一样」。最重要的一格是**面缺席 ≠ 面坏了**：宿主没装那个扩展、本版没接那一面，都属于「没测过」，报成坏会造成一批假故障（自检直接断言「面缺席即使自述不可用也必须判未验证」）。
- **接口存在不得报成服务可用**。观测分四级（服务 / 接口 / 版本 / 无）：只知道接口在场 ⇒ 最高只能到部分可用；只知道版本号 ⇒ 未验证（版本号不是可用性）。这一条单独成 `apiOnlyDegrade()` 而不是内联 —— 它是最容易被后人改坏的一格，自检与判据双向钉住。
- **缺能力必须给替代操作**：六项能力各有一组替代操作，顺序即优先级，由内核声明、原样转述到界面（视图不得自己排）。未验证**不给**替代操作 —— 给未验证项塞一份替代路径，会把「跑一次就好」误导成「已经坏了要绕路」。
- **能力检测零写入零模型调用**：咽喉那一层只调只读出口 —— 搜索只探到引擎的 `listSources()`、记忆读上游自述态、图片只读管理器配置（**绝不出图**）、语音只检查 `getUserMedia` **在不在**（**不调用** —— 调用会弹授权弹窗，那本身即副作用）、通知真读一次读路径、恢复交接读世代号与被挡日志。读数里带 `writes: 0`（字面事实，不是声明）。

跨仓版本联动不在这里写门限常数：上游最低版本**从登记面真源派生**（`minUpstreamOf` 取该 owner 名下最大的 `since`，`null since` 不参与比对）。版本偏低与版本读不出分列两账（`outdated` / `missing`），没有门限就**不判版本偏低**（如实少一条判据，好过拿假门限比）。上游版本归因只在**恰好一个上游立了版本判据且来源 id 能对上名字族**时进行 —— 认不出就报「读不出」，不猜。

诊断报告文本的唯一实现在内核 `capHealthReport`，由咽喉调；**「复制」这个动作本身不得触发检测**（只用已判定的读数拼，`report` 分支里不出现观测采集函数）。

宿主版本按「先问 API → 再问 `getContext()` → 最后问页面元素 `#version_display`」多来源试读；全拿不到就**如实空串**，界面写「读不出 —— 这是「读不出」，不是「宿主不支持」」。这两句处置相反：读不出要人去确认装没装，不支持要人换环境。

## Alternatives considered

- **在视图里自己判四态**：视图已经拿到六项观测，就地分档最省事。但那就是同一口径的第二份实现（本仓治过多次），且「接口在不在」与「服务可不可用」的界最容易在视图层被抹平。故视图只 import 文案表、只挑样式类名，判定全部走内核。
- **能力检测放在 App 打开时做**：让 App 自己探更顺手，但 App 层探针必然带上渲染时机与交互副作用（尤其是语音那一格），且诊断面要另写一份探针 —— 同一读数的两个来源必然漂移。故观测采集只有一个咽喉取数口，App 与诊断面都只读那一份缓存。
- **宿主版本读不出时写「不支持」**：短、好懂，但把「读数缺席」和「能力缺失」压成一句，正是本仓最贵的一类错读数。故读不出即如实说读不出。

## Consequences

**本版修掉的两处缺陷，都不是判据抓的，是本版自己在侦察里实测撞出来的 —— 两者都不会报错，只会静默显示错的东西：**

① **类前缀族撞车**（侦察样式投递时撞见）。本模块原用 `.ch-*` 族，而金手指 App（`apps/cheat`，v2.47.0）**已占用**该族，两者有**八个类名逐字重名**（ch-root / ch-head / ch-title / ch-badge / ch-btn / ch-note / ch-pre / ch-row），且取值方向相反（金手指是深色鎏金全屏、能力体检是浅色卡片）。按样式投递机制把内容并进 `phone.css` ⇒ 同名选择器互相覆盖，**金手指界面当场走形**，而 registry 门只看「前缀族在不在 phone.css 里」，**看不出撞车**。已整族改名 `.cph-*`（用负向后顾正则 `(?<![\w-])ch-` 改，不误改 DOM 契约 `data-ch-act`），并把 `.cph-*` 整块投递进 phone.css；判据新增三条钉住（族名对 / 无裸 `.ch-` 残留 / 能被 phone.css 找到）。

② **三层与咽喉缓存键名错位**。咽喉写 `hostVersionText` 且**没有** `readable` / `why` 两格，而 App `_vm()` 读的是 `hostVersionLine` / `host.readable` / `host.why`。三处对不上 ⇒ 宿主版本明明取到了、界面永远显示「还没取到」；`faceReadable` 恒为 false ⇒ 界面永远挂着一条「能力面取数口不在位」的红字（**假故障**）。修法两侧同时改：咽喉缓存补 `readable: true` 与 `why: ''`（缓存在场即读数可读，不可读的唯一形态是咽喉未挂、由 `capHealthFace()==null` 表达），App 改读 `hostVersionText`。判据 C1 把这组键名逐格钉住。

两处都属于「不报错的真缺陷」这一族：门禁看不出，跑起来也不抛异常，只是用户看到的东西是错的。这也解释了为什么本版把「键名逐格对齐」单独写进判据 C 面，而不是靠约定。

**本版挡得住「看起来没坏但显示不对」这一族里的四个具体形态**：面缺席被画成「坏了」、接口在场被画成「服务可用」、宿主版本读不出被写成「不支持」、上游版本读不出与版本偏低被合成一句。

**本版不能保证**（与 `docs/runtime-verification-boundary.md` 同源）：① 真宿主里 `#version_display` 的实际存在性与版本号格式（本版是多来源试读 + 读不出即如实说，不假定它一定在）；② 六项能力在两台桥都缺席的真机上的观感；③「复制诊断报告」在无剪贴板权限环境下的降级体验（代码里已降级为「显示在下方手动选中」，但观感未实测）。

浏览器实机与全量 `npm test` 仍属第二期收官验收范围；不得用定向测试冒充完成。
