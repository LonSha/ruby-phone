# Agent Note: 创作工作台的检查与委托边界

Status: implemented

## Problem

v3.70.0 的 creation-pipeline 建好了八来源、六目标、草稿构建与幂等账本，但产品端只消费了其中一个导出（normalizeCreationLedger）；素材选择、发布前检查与发布本身在用户侧仍各自孤立。草稿与已发布在账本里共用同一批字符串状态，published 从未被任何代码写过。

## Decision

素材按五类声明（角色 / 事件 / 图片 / 曲目 / 文本），每条带可回溯到来源 ID 的引用键；每一类的状态三态不同形（读不到 / 读到但空 / 读到有）。发布前检查固定四类：缺素材（含坏图与缺播放器）、坏链接、目标权限三类为硬拦截，敏感标记为需确认。发布动作只委托五个目标 App 的真实写口（微信朋友圈数据层、微博正文、Pixiv 作品、杂志稿件、同人货架），工作台本身不调用任何写口。幂等键直接复用 creation-pipeline 的实现；发布台账与草稿账本共用同一套归一器，不复制第二个状态源。

## Alternatives considered

- 新建第二套素材状态：最直接，但会让同一素材在两处各自演化，且违背 R-X6 验收里的不复制状态源，故不采用。
- 直接在各 App 里加检查：省一层调用，但检查口径会散成五份，本仓六次欠债都源于同一口径抄多份，故不采用。
- 把创建 pipeline 的导出清单重做：会破坏 v3.70.0 的既有判据（导出恰好十一项），故改为新增工作台内核引用它，而不是改写它。

## Testing

定向套件 tests/system-v3900.test.mjs 六面 21 条：结构与注册、纯函数与视图数据面、五类三态、四类拦截、只委托真源、零第二状态源、引用可回溯、上下文素材不作载荷，加八条真源码破坏负控制（每条在同款判据上必转红，第八条为两向对照自证）。探针基线由 tools/refresh_baselines_v3900.py 现场对平。浏览器实机与全量 npm test 仍属第二期收官验收范围；不得用定向测试冒充完成。

## Consequences

发布路径从各 App 各自为政变成咽喉唯一入口，代价是多一层调用与一次回读确认；换来的是坏图与权限不符不会显示发布成功，且同一素材不会写出第二份状态。
