## 迭代 195 · v4.36.0（2026-12-29）

- 【版本升至 4.36.0（五源同源）：第五期 R5-O9 追问条件可见、可改，时点不误写成以后】追问那一屏此前对**任何**时点都只写一句「时点 ≥N楼」，而「截至第20楼她住哪」（上界：只看到那为止）与「第20楼以后呢」（下界：从那起往后）在**同一个数字**上落出**相反**的方向。用户读到「≥20楼」会以为从那时起往后都算，而真实查询恰恰相反 —— 不报错、只是错读数，且**数字看着是对的**（本仓最贵的一类）。
- 【契约件新增时间方向三态与唯一出处 timeConditionLine】`at`（下界）/ `as-of`（截至当时，上界）/ `since`（从此以后）三句**互不相同**，另加一格「给了但不认识」。为什么必须分列：方向是**查询语义**，不是显示修饰 —— 同一个数字两种相反的查法，合成一格就有一类问句必然答错。
- 【方向不认识 ⇒ 不许按 ≥ 兜底】旧口径那条错读数就是靠「不认识就往 `≥` 落」形成的。本版把「不认识」单独成句（「方向不认识，未按任何方向查」），并且它与「上游没给方向」**不同形**：前者要说清没按任何方向查，后者是**旧口径的既有语义**（M5-O1 之前上游根本不产方向，那时 `atFloor` 就只表示下界）。
- 【旧口径一字未动】`at` 与「上游没给方向」仍读作「时点 ≥N楼」—— 历史读数与既有判据（v4220 B2）锁着这一句；为修「截至当时」而把所有时点改成「方向未定」，会把历史读数一起改错。
- 【上游内核增条件清除（R5-O9 的唯一委托口）】`advanceThread` 收 `opts.clear`，可清轴表 `QT_CLEAR_AXES` 随面导出。顺序是**先按本句算新值、再按清除表抹掉该轴**：本句自己给出的新值（「清时点，看第30楼」）**优先于清除** —— 用户明说的那一句比一个界面动作更具体，被它盖掉才是错读数。
- 【清不掉的一律具名，四形各不同】轴名不在表里 / 本会话本来就没有这一轴 / 本句新设优先 / 清成了什么 —— 四件事分开说。「清掉了」与「本来就没有」压成同一句，用户会以为自己那个动作生效了，而其实这一轴从来没被继承过。
- 【控制器 clearAskCondition / askClearAxes / askTimeLine 三口】清除表**原样下传**（合法性只有上游那张表说了算，本层再判一份就是第二个真源）；轴名不在表里时**点下去那一刻**就说清，不必等一轮往返；没有追问出口时**不许**回落普通问答假装清过了。
- 【视图时点行 + 可撤条件按钮】轴名照上游给的那张表画按钮（视图**不另立清单**：两份清单迟早分叉，而分叉的后果是「按钮点了没反应」）；时点单独一行显示 —— 它与「人物」不是同一类条件，用户判断「这一问看的是哪一段」只需要这一句，混在人物后面会被读成附注。
- 【轨迹行也报方向与清除】轨迹是「只回看条件」的那一屏，而「按哪个方向查的」「这一轮清掉了什么」正是条件本身。回看时看不出方向，等于条件没记下来。
- 【与上一版的接续：R5-O7 的取消/任务身份 + R5-O8 的**回源核对**分片让出形态】计划原文写的是「O7 的取消/任务身份可复用但非强前置」——本版把它真正复用起来，不是另起一套：可撤条件的委托口与**取消/任务身份**同规（换会话、再点一次、上游复位三件事的正确处置是一样的：都不许把上一轮的条件画到这一轮），而清单分片与 R5-O8 的**回源核对**分片同规（阶段入口先让出一次，空集合也留一个受理窗口）。R5-O8 那两处形态（读口只认 `chapters`、阶段入口先让出）在本版各有一处同族落点。
- 【本版自己抓到的两个缺陷形态】① 首版把「上游没给方向」也写成「方向未定」——那会把历史读数一起改错（`at` 与空在旧口径里语义相同，只有「给了但不认识」才该单独成句）；② 首版 D1 负控制写成「破坏后与 since 同句」，而真实落点是掉到末尾的 `≥` 兜底 —— **破坏写法不足**会让负控制假绿（破坏确实发生了，但判据判的不是那个落点）。
- 【判据 tests/system-v4360.test.mjs 二十一条】六组：口径（方向三态唯一出处、旧口径句式不变、可清轴表唯一出处、纯契约零副作用）/ 内核行为（三种方向三句不同、as-of 不得出现「以后」、不认识不许兜底、清除读数分列、无时点条件给空串）/ 接线行为（清成了 / 没清成 / 本句新设优先 / 轴名不在表里 / 没有出口不许假装清过 / 视图接线）/ 四条定点破坏负控制（每条配原版必真的反向对照）/ 版本锚。
- 【不做：不让手机另造问句解释器】清除与方向全部**委托上游**：thread 归上游持有并随聊天持久化，本层自己抹一格，下一次追问上游照样按它记着的那份算 —— 界面显示清掉了、实际没清。
- 【不做：不只把 ≥ 改成 ≤】改成 `≤` 只是把一类问句的错读数换成另一类的错读数（「第20楼以后呢」会变成「只看20楼之前」）。本版动的是**方向**这一格：三种方向各自成句，且「不认识」不许兜底。
- 【看起来没坏但显示不对】本版两处缺陷都不报错、不崩界面，只是「截至当时被读成以后」与「清掉了其实没清」。
- 【运行时验证边界】本版未做浏览器/真宿主取证。「清除后真正查询全范围」属**上游查询层**读数（清掉时点后实际扫了多少楼），归上游与真宿主门；本版判的是它的可判定前件（清除真的下传了、读数如实、清不掉时不许报成清掉了）。docs/runtime-verification-boundary.md 的当版实测数字由 tools/refresh_doc_readings.py 现场跑两道门写入。
