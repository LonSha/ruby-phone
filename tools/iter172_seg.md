## 迭代 172 — v4.13.0 · 第四期 R4-O1 往事答案真正可点开出处
# 占位:下列条目由 tools/bump_v4130.py 写入 ITERATION_LOG.md 与本版 update-log 条目
- 【本版做的是第四期优化项第一件:R4-O1 往事答案真正可点开出处】计划原文要的是「从『相信一行摘要』变成『点开原文核对』;答案显示友好出处、命中句和前后文,返回后保留问题与结果」,并带一条明确的不做清单:不复制原始聊天、不新增来源台账、不把账本缩写当唯一用户文案。
- 【修前实测的缺口有三层,一层比一层深,统统读码可复算】最浅一层:apps/memory/memory-view.js 的 _askFaceHtml 把答案行的出处渲染成一个普通 div,「出处:承诺 · 第 12 楼」只是一行字,答案行上没有任何跳转按钮,而注释与计划都写着「可点开」——给人读的那一句与真码脱节。第二层:config/memory-qa-contract.js 的 qaRefOf(能把上游 {ref, floor, ledger} 归一成九账行身份)与 config/open-ref.js 的 applyOpenRef(能投跨 App 靶心)早在仓里,而全仓实测 qaRefOf 只被测试与门禁清单引用,产品面零命中——这是本仓被点过六次的同一形态「建好不消费」。第三层也最根:仓库里根本没有「跳到主聊天第 N 楼」这一口,grep scrollToFloor 与 gotoFloor 与 jumpToFloor 全部零命中,于是即便视图长出按钮也没地方可去。
- 【新契约件 · config/source-locator.js(209 行纯函数)】六态互不同形是它的核心设计:chat 有合法楼层 / memory 无楼层有引用键 / no-target 两者都无 / ref-invalid 有账名无引用键 / location-unavailable 本版宿主没有定位口 / not-found 宿主跑了但那一楼不在了。压平任意两态都会造出处置相反的两件事长得一样——「等升级」与「去翻历史楼」在界面上同形是本仓最贵的老账。
- 【楼层走全仓唯一取值门】config/num-gate.js 的 numOrNull 是唯一实现,本件引用它而不是自持一份:Number(null) 恒等于 0,不设门就会把「没给楼层」读成「就在第 0 楼」,而 0 在本仓是合法楼层。判据同时守两向:怪值必须如实 null,而 0 与 '0' 与 ' 5 ' 必须如实出数(门不得关成「谁都取不到」)。
- 【「不回报 = 没成」写死在 locateTarget 里】宿主口返回非对象、缺 ok 字段、ok 为非布尔一律算没成,归因 host-silent。这条是刻意的:本仓最贵的缺陷形态正是「函数没抛错、只是默默没生效」,而它在这里的表现会是「用户点了按钮、界面毫无反应」。
- 【宿主侧新增唯一一口 · index.js 的 locateChatFloor】修前那一族能力在宿主侧根本不存在,本版把它建出来:过 stFloorOrNull 门(0 是合法楼层)→ 取宿主 chat 上下文 → 按 #chat 下带 mesid 属性的 .mes 找元素 → 滚到该楼 + 短促高亮 + 收起手机面板(否则用户点了按钮仍盯着手机屏,是「点了没反应」的另一种形态)。归因里刻意没有一种叫「点了但没到」:chat-unavailable(上下文取不到)与 not-rendered(消息在但 DOM 没有)与 not-found(楼超出 chat)三态分开报。
- 【两侧照同一个名字接线,不各写一份】宿主挂载用契约常量 HOST_LOCATE_METHOD 做键(window.VirtualPhone 上挂这一格,恰中一处),手机侧 locateTarget 按同一个常量取这一格。名字若在两侧各写一遍,漂开的表现就是按钮点了没反应,且不报错——本版把这条钉成判据(挂载点必须恰中一次且用常量)。
- 【视图侧:出处行从一行字变成可点开的靶心】新增 _srcHtml 与 _goSource 两个方法,前者按靶心态排版(只有能去的两态才给按钮,其余四态如实念出为什么不能去),后者是容器级委托里的唯一消费点。两类靶心分派互不相同:chat 靶心交控制器取数口(它调宿主定位口),memory 靶心派跨 App 事件并收起记忆 App。
- 【memory 靶心的 ref 不手写】九账行的 kind 归属是登记面的事(config/open-ref.js 里登记 memory 归属 summdesk),消费侧各处手写对象字面量会在归属一改时静默失配。本版把这支笔收进 source-locator.js 的 sourceOpenRef 一处,视图只调它——判据钉住视图里不得出现手写的 kind 字面量。
- 【取数层只转交,不判形态也不碰 DOM】apps/memory/memory-app.js 新增 locateSource 一口,内部只做 normalizeSource 与 locateTarget 两次真源调用。这是本 App 既有纪律的延续(视图只吃投影后的数据、不摸 window);出处定位属取数事,与渲染无关。
- 【本版自己抓到的缺陷形态两处,都在判据自身上(合并前逐条修掉,留痕)】一 A1 首版把原始对象直接喂给 sourceLocatorLine,而那个函数吃的是已归一的靶心,于是三个值得不同的输入全落进同一分支,当场得到 3 而不是 6——判据自己错了,不是实现错了,分辨它们靠的是「先问这一条断言在原版上该不该真」;二 负控制 D3 的破坏锚点缩进写了一级,锚点零命中直接抛,锚点不唯一即抛这条纪律当场救人。
- 【交棒改写】本版把 R4-O1 的验收从「答案行可点」交棒到「六态各有各的处置词表」那条路,并把「宿主有没有定位口」从隐含假设交棒成显式可查的一态(location-unavailable);相关各条判据一律写成下限形,下一版抬版无需二次改写。
- 【运行时验证边界(如实声明)】本版在无头环境验证的是:六态互不同形与六句归因文案两两不同、0 是合法楼层而五种怪值不塌成 0、locateTarget 的九种宿主回报(其中七种是没回报)一律算没成、sourceOpenRef 与登记面归属一致、宿主口与视图按钮与控制器取数口三层真接线、样式两侧投递。**未做**真实宿主下「用户在真机上点开一条出处、那一楼是否真的滚到眼前、删楼之后那一格是否如实报失效」——那需要在真机浏览器里走一遍旅程;自动化门禁能保证结构正确与接线完整,但它不能保证真机上的视觉排版与滚动行为。
