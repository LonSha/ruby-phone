## 迭代 245 · v4.111.0 · 第十三期 R13-X8 复述：宁可复述得笨，不许复述得假

- 【版本升至 4.111.0】R13-X8 复述：在召回台第五页签问一句「我们之前聊过搬家的事吗」，能收出带出处的几段过往，每条原话都能点回原位置（两件内核 + 页面签 + 25 项判据，含计划书点名的那条负控制）
- 【本版做什么】两件内核按「口径」与「算法」分层：config/recall-narrative-terms.js（4508 字节，零 import 叶子：三态闭集、五因由闭集、停用词表、六项限额、排序口径）、config/recall-narrative.js（10794 字节，主题词抽取 + 扫描 + 归并 + 结论截取 + 引用核对 + 一句话读数）。只拆两件而不是三件：主件未超该项 11K 预算，再拆只会让算法跨文件跳
- 【本版治什么】聊天史只能靠翻：既有全局检索是连续同序包含，「聊过搬家的事」这种说法在真聊天里基本搜不出东西；即便搜出来也是一堆散条，用户拿不到「那是哪一次、当时说到哪了」。本版不改检索，只在其上加一层：把散条收成段，并给每段一个出处
- 【本版做什么】两件内核的三条不变量：其一引用必须真，所有 id 只在自己扫过的行上取，取不到的行整条丢弃并记一条 bad-id 因由，不给空串充数；其二归并只有两条规则（楼层间隔小于六且时间差小于四十五分钟才算同一段），不做语义聚类，因为那需要模型，而模型会编；其三是结论只截取不生成，取该段最后一条原话，超出一百二十字加省略号，取不到就如实交空串并由界面写「不替你总结」
- 【本版做什么】入口接在 apps/recall 而不是聊天页：计划书给的两个入口里，聊天页是 946383 字节的巨兽（P8 约束），而这条能力与召回同一个主题——召回台管取回的路，复述管取回之后怎么讲。App 侧加现取聊天数组与 narrate 取数口，视图侧加第五页签、输入框、三态三色、因由徽章与段列表，样式加二十一条
- 【自己抓到的缺陷形态】跳转初版走的是跨 App 打开引用，用了 message 这个 kind：而本仓 OPEN_REF_KINDS 只登记七个 kind（expense / memory / item / song / novel / illust / article），message 根本没登记，会被判 ref-kind-unknown 而不投。这不是「写错一处常量」，是「同一件事有两条路，其中一条没铺完」。修法是改走既有唯一出处定位路：normalizeSource 归一靶心、locateTarget 投宿主 locateChatFloor，并把三种失败处境分开说（宿主没定位口要等升级 / 那一楼没了要去查历史楼 / 宿主没回报要报缺陷），三者处置相反
- 【自己抓到的缺陷形态】楼层未知时不许拿 0 顶替：0 是合法楼层即第 1 楼，拿它填「不知道」会把用户送到错的地方。修法是楼层空串时传空值而非 0，把「不知道」与「第一楼」在类型上先分开。同形的坑本仓在 num-gate 早就治过一次（Number(null) 恒等于 0），本条是它在界面侧的第二次现身
- 【自己抓到的缺陷形态】判据自己写坏两次，两次都是破坏选错方向而非内核有错：其一「时间不可知排后面」用两段数据测，两段时无论把未知当成最小还是最大，比较结果的符号都不变，规矩坏没坏看不出来，必须布三段才可观测；其二排序破坏只改了一支，比较器因此不对称，同一对元素反向比较得相反符号，排序结果依赖引擎调用顺序，判据红了但红的原因不是它要守的东西。两类都归到「破坏只改了一半」这一形态下
- 【交棒改写】dead-export 与 bind-audit 当场抓到一个只声明不消费的导出（排序口径常量 RECALL_ORDER）：注释里写着「排序口径写在数据里」，算法件却把方向写死成倒序。修法不是删常量，而是让排序真读它——否则那句注释就是假的。这与本轮 X2 收口时那句「手抄清单必然会漏，能算就别抄」是同一件事的两面：口径写在数据里就必须有代码在读它
- 【运行时验证边界】判据证明的是引用真伪、归并两条规则、结论截取、三态不同形、跳转唯一路径与四条真源码破坏，不证明真机上归并得好不好——计划书明写归并质量不保证，本项只保证引用的每一条都真存在、可回源。另：本版零写入面，没有存档要撤销，故没有「撤销后逐字一致」这一类判据
