## 迭代 238 · v4.104.0 · R13-O8 回收站（唯一软删实现：11 个 App 接线 + 设置页分区 + 判据六面）

- 【版本升至 4.104.0（五源同源）】manifest.json / package.json / index.js 版本常量与公告块 / update-log.json 的 latest 与 head 与新条目 / tests/audit/status-ledger.json 的 version 与四处 version_sources 一次抬齐；ITERATION_LOG 新增本迭代段并把元信息「当前版本」行改当版；边界文档按当版复校。抬版沿用仓内范式脚本（本次 tools/bump_v4104.py 对齐 tools/bump_v4103.py，只换 STEPS 与头注，逻辑一字未改）。
- 【治的欠债：删除这条路上此前没有回头路】v4.102 之前全仓的删除都是硬删 —— deleteEntry / deleteMemo / deleteMoment / removeSong / removeBook 各自 splice 完就落盘，clearAll 类更是整段清掉。删错了没有任何补救，而删除恰恰是用户最贵的那个操作：写一条要 AI 生成加人工编辑，删一条只要一次误触。
- 【更要紧的是「回收站」这个词在仓里早就有三套语义】相册 / 日历 / 日记各自有一套名字相近的本地实现，但互不相同：有的只藏图不藏条目、有的只是软隐藏标记、有的删完还能从备份里捞回来。三家各写一遍的后果不是代码冗余，而是用户学到的「删了能回来」在三个 App 里长得不一样 —— 这正是本仓一直在治的那族形态：同一件事有好几个说法。
- 【路径：新建 config/recycle-bin.js 作为唯一软删实现】445 行、11 个导出，只做四件事 —— 收一条记录、列出来、取回去、彻底清掉。它刻意不碰任何业务数据：不认识日记、不认识微信、不认识相册；真正「怎么从这份数据里摘掉这一条」仍由各 App 自己的 hard 回调执行，因为那只有 App 自己知道。
- 【为什么 id 必须原样回来（不是洁癖）】本仓大量数据是跨 App 引用的：日程备忘被生活线按 calendar 前缀挂着、日记配图按 bg 加 id 存在设置里、微信消息被存档按消息 id 引用、阅读进度按 bookId 存。恢复时若重建一个新 id，这些引用全部断成孤儿，而且不报错，只会在某个二级页面里悄悄少一行。故 restore 只做一件事：把当初存下的 payload 原样交回，其中 payload.id 一个字符都不改。
- 【为什么默认行为必须零改动】既有调用方一律不该知道回收站存在。故记录存在自己那一格里（recycle_bin_v1），业务数据被真的摘掉了，列表里自然没有它 —— 不需要给任何查询口加「where 没删」这样的过滤。这是刻意取舍：加过滤会让 88 个 App 的每一次读取都多一个分支，而分支写漏一处就是「删掉的东西又冒出来」，比不软删还糟。
- 【两条键的隔离意图必须不同，且用不同前缀】记录格 recycle_bin_v1 走精确匹配的会话隔离（删掉的是这段会话里的东西）；开关格 recycle_bin_enabled 是全局的（用户对这台手机要不要回收站的偏好不随角色切）。刻意不共用前缀 —— 若两个键共用一个前缀模式，开关会被一起隔离，切角色后「回收站莫名又打开了」，正是 keys 门 K2 要抓的那种意图与机制不一致。
- 【四条降级路径全部仍然执行删除】开关关掉、payload 序列化失败（循环引用）、单条超限（30 万字符）、写盘失败 —— 四种情形都仍然调用 hard。理由写在注释里：回收站坏了不该让用户的删除操作跟着炸，那种故障会把「删不掉」变成新的用户可见问题。四条各自如实报一个成因码（disabled / not-serializable / too-large / bin-write-failed），不把没留说成留了。
- 【顺序纪律是先落回收站再真删】反过来的话中途崩溃就是「删了但没留」，而这条路上没有任何别的补救手段。批量入口 softDeleteMany 同样守这条：把全部 hard 收集起来、写盘成功后才一次性执行。批量入口存在的理由不是整齐：微信「从这条删到尾」一次几百上千条，逐条调 softDelete 是 O(N 乘 M) 的落盘量，实测会让删除按钮卡住好几秒。
- 【上限 200 条是有界账本，且必须保住新记录】超限从最旧的真删，绝不静默丢新记录 —— 用户刚删错的那一条必须在回收站里，这是本模块存在的全部理由。它的另一面也如实写进注释与界面文案：清空 500 条日记时只有最后 200 条能回来。
- 【meta 面必须与 payload 严格分离】payload 必须是业务对象原样，往里塞 index 之类的私货会污染业务数据（用户可见，也会被下一次逻辑当成真字段）。故位置线索单列一格：diary 的 index 加两个配图键、微信消息的 chatId、打卡项的 cardId（项 id 只在卡内唯一，跨卡会撞车）。恢复器签名是 payload 加 meta，且必须容忍 meta 为空并退化成追加到末尾 —— 位置丢了还能恢复内容，位置丢了就判失败等于「因为排序信息没了所以不让你恢复」。
- 【恢复的四道闸，每道都有具体理由】entry-missing 报没这条；restorer-missing 不动回收站（App 本次没打开过，打开后可重试）；payload-missing 报没存正文；id-drift 拒写（payload.id 与条目 id 不一致即拒，因为写回新 id 会让跨 App 引用断成孤儿且不报错）；apply-failed 把条目留在回收站（失败可重试，丢了不可重试）。八条成因码全部有中文人话，直接摆到界面上。
- 【接线覆盖 11 个 App 共 19 个删除点】diary（单条 / 批量 / 一键清空三点）、calendar（备忘 / 假期两点，恢复时重建派生生活线）、music（歌）、reading（书）、weibo（动态，恢复时把计数加回）、phone（通话 / 联系人 / 短信 / 短信会话四点）、wechat（朋友圈 / 消息 / 批量删 / 从这条删到尾 / 整个会话五点）、mofo（工坊条目，恢复须撤墓碑）、focus（任务）、punchcard（卡 / 项两点）、piggy（流水 / 亲属卡两点，恢复走状态归一化重算余额）。落在 apps 侧的 11 个数据类构造期登记恢复器，注册表在 config 侧，依赖方向仍是 apps 到 config。
- 【各 App 恢复语义里那些刻意的不完美，逐条写进注释】音乐恢复追加到末尾而不是原位（歌单是有序队列，插回原位会打断用户后来的排序意图，歌回来了比位置也对更重要）；阅读恢复的是还认得这本书的那一条而非能直接翻开的书（章节惰性加载，重启后本就要重新导入）；微博的图片文件不进回收站（文件清理是前端 ImageManager 的活，链接在 payload 里但文件若已清则恢复出来是坏链）；家教的墓碑必须撤（不撤则条目回来了但下次合并又当已删跳过）；存钱罐恢复走状态归一化重算余额而不是手写加减（否则流水分回来了、罐里的钱没回来）。
- 【设置页新增「回收站」分区：本项唯一的用户可见入口】按 App 分组（分组顺序等于最近删除时间倒序，用户找的是刚删的那条而不是字母序）、每组带条数、逐条显示删除时间与有快照与否、逐条恢复、逐条彻底删除、清空（二次确认两段都要点到）、以及一个开关。列表刻意不载 payload —— 200 条乘每条几十 K 的正文在渲染时一次性复制一遍是本仓踩过的卡顿形态。
- 【捞不回来时必须说出原因，不许把失败画成一个什么都不发生的按钮】restorer-missing 最容易被我方当成 bug，它其实是「那个 App 这次会话还没打开过」，界面直接翻译成人话：请先打开对应的 App，再回来恢复（回收站里的记录还在）。清空动作必须给确认令牌，不给就返回 bad-confirm 拒绝执行 —— 而不是弹个 console.warn 然后照删。
- 【本版自己抓到的真缺陷：restore 后回收站里还留着那一条】restoreById 里写成从 detach 只取第二个返回值，把「摘掉之后的数组」丢了；随后又把这个原数组写回盘 —— 两个错叠在一起，后果是恢复成功后回收站里仍留着那一条，用户能再点一次恢复、业务侧就多出一份，而两次「恢复成功」的提示都正常、界面上看不出任何异常。由本版判据 B1 的「restore 后回收站为空」当场报红才发现，修法是把新数组接住并写回它。
- 【本版自己抓到的第二个缺陷形态：降级路径写对了，兜底却写反了一处】首版 restoreById 的注释里明写着「失败可重试、丢了不可重试」，而代码在 restorer-missing 与 id-drift 两条路径上确实没动回收站 —— 这两条是照注释实现的；真正漏的是成功路径没销记录，属同一族「注释说了、机制到不了」的姊妹形态：注释说了「取回去」，而取回去之后没把记录销掉。留档在此，因为这两处的距离只有一个变量名。
- 【新增判据套件 tests/system-v4104.test.mjs：六面共 18 例】A 面四条降级（成功 / 开关关 / 序列化失败与超限 / 上限先进先出保住新记录）；B 面端到端跑真 DiaryData（删 → 列表没 → 回收站有 → restore → 列表有且 id 逐字相同、配图键一起回来、位置回到原 index、restorer-missing 与 id-drift 不销记录、清空需令牌、一键清空也进站）；C 面批量一次落盘且全部 hard 都执行、同批 binId 不撞；D 面设置页真消费七个出口（防内核写好了、导出挂出来了、产品端零消费）；E 面四条负控制。
- 【负控制走「真源码破坏再落副本」这一形，不是模拟常量】四条各自把真源码按锚点 split 后落成临时副本并从副本 import：把 restore 改成重建新 id、把清空令牌校验改成恒假、把开关判定改成恒假、把设置页一个出口调用抹掉。四条都实测转红，且每条都配一条正向自证（真源码上同款判据必须为真）。破坏锚点必须恰中 1 次，中 0 次即抛 ——「破坏没发生也绿」是本仓登记过的三种假绿之首。
- 【判据侧自身错两处（不是产品缺陷，逐条留档）】其一，破坏副本有自己那份模块级 RESTORERS 注册表，真仓的登记不会流进去，于是负控制报的是「没登记」而不是「id 漂移」—— 修法是给副本补登记一份等价写回口，刻意不是替身简化：恢复语义没变，变的只有 recycle-bin 交出 payload 那一步；其二，开关关闭判据把「写开关那一次」也算进了删除的写盘计数，期望值差一，改用删除前后取差。
- 【交棒改写与下限形两处】keys 门的 storage 键使用点从 507 走到 508、CHAT_DATA_PATTERNS 从 162 走稳、登记从 507 走到 508（会话隔离 312 / 全局 193 / 历史键 3）；新增的设置页展开态键 phone-settings-recycle-bin-open 必须是全局，同族 general 系键全部如此，登记时把这条理由写进注释 —— 否则下一版很容易顺手把它划进会话隔离。
- 【读数】v4104 套件 18 例全绿；keys 门 508 使用点 508 登记全绿；MATRIX 89 行不变；回收站可恢复的 App 面 19 个键（超过计划建议的 10 个下限）。定向回归：syntax / import-resolve / named-import / keys / registry / bind-consuming / method-consuming / dead-exports / lifecycle / weak-coercion / source-derivation / bridge-contract / screen-host / session-writeback / hardlink-safety / doc-path-claim / upstream-face 逐门单独跑，不做全量。
- 【运行时验证边界】本层只证明软删语义、端到端 id 保真与产品面接线的源码层成立，并把四条降级与四条负控制做成会响的判据。它不证明真宿主里回收站的落盘、会话隔离与换会话重绑实况；不证明图片类删除的恢复效果（图片文件不回收站，可能坏链）；不证明恢复在「App 本次没打开过」之外的时序情形；也不证明回收站在宿主清缓存后仍在。以上均归 R-O3 / R-O2 家族：这类形态的共性是**不报错、不崩溃、只错结果**。
