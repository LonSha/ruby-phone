- 【三态不同形：计划原文点名的纪律落地】内核没接上（宿主无 / 中枢无 / 内核无 / 读抛错）与某域取到但 0 条、某域取不到，是三件不同的事，不许粉饰成同一句话。桥接层把它们分三档：ready（count 大于 0）/ empty（count 为 0，该域暂无数据）/ missing（ok 为 false，数据源没取到，不是没有内容）；一句话读数另有四档文案（零命中 / 内核没挂上 / 读抛错 / 正常），实测三句互不相同（C1 判据钉死）。塌成一格就是把「系统坏了」说成「没搜到」。
- 【SETTINGS 域灌的是 App 注册表，命中行自带直达落点】四域里 CONTACTS 取 phone_call_contacts 并集 cachedWechatData.getContacts，WECHAT 取 wechat_data.chats，DIARY 取 diary_entries，SETTINGS 取 APPS 注册表 —— 搜一个 App 名就直达那个 App（每行带 deepLink.targetApp，走 config/app-open-detail.js 的 buildOpenDetail 同一支笔，不手写对象字面量）。这也正是计划里「同时作为 R11-O7 应用库搜索的后端」那句话的落点。
- 【本版自己抓到：负控制 verify 方向反了（三条 G 首跑全红）】首跑 17/20，G1/G2/G3 三条负控制全红。根因不在实现，而在判据：首版 verify 断言的是「破坏之后仍应等于正确值 / 仍应单列 / 仍应被截」—— 这是把负控制写成了对破坏结果的期待，破坏没发生时反而会绿，破坏真发生时才红，方向整个反了。修法：抽出 faceCriterion 三个纯谓词（triState / missingIsSpoken / limitHolds），每条负控制先断言「同款判据在原版上必须为真」，再断言「同款判据在破坏副本上必须为假」—— 双向都钉住，判据本身假与被测对象坏才分得开。修后 20/20。
