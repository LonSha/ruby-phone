## 迭代 173 — v4.14.0 · 第四期 R4-O2 问答与检索可取消、可继续操作
# 占位:下列条目由 tools/bump_v4140.py 写入 ITERATION_LOG.md 与本版 update-log 条目
- 【本版做的是第四期优化项第二件:R4-O2 问答与检索可取消、可继续操作】计划原文要的是「大库搜索时仍可输入、返回、换会话;快速连续提问只展示最新一次结果」,验收原文两条最硬:旧请求不覆盖新问题、取消在下一协作分片生效;并明写不做新增后台检索服务或性能监控平台。
- 【修前实测的缺口(读码可复算,不是推演)】apps/memory/memory-app.js 的 askPast 走 config/memory-qa-contract.js 的 readMemoryQaAnswer,落到上游**同步**出口 askMemoryQuestion。而上游 lonsha-memory-plugin 在 v3.332.0(M4-O4)早已交付异步出口 askMemoryQuestionAsync(逐条计划走 queryAsync,片间让出主线程,自带 taskId 与 shouldCancel 与 onProgress,回执在同步版全键之外增 async 与 taskId 与 state 与 processed 四键),本仓实测 grep askMemoryQuestionAsync 在 apps 与 config 与 index.js 三处**零命中** —— 又一次「建好不消费」。后果是大库上按一次「问」就是一次同步全量扫描:面板不动,连按两次只会得到两条串在一起的结果,旧的那条可能后回来把新的覆盖掉。
- 【新契约件 · config/ask-request.js(纯函数,231 行)】只回答两件事:这一条回信还是不是「现在这一次」(代际判定),以及该不该停(交给上游 shouldCancel 的谓言)。为什么不能用「清结果」代替:清结果只能拦住**还没出发**的那一轮,拦不住**已经在跑**的那一轮回来时把旧命中写回面板 —— 这一形态本仓在搜索侧治过一次,本件不再复刻第四遍。
- 【运行态六态互不同形】running 正在问 / done 问完 / canceled 用户取消了(下面是已处理部分) / stale-dropped 旧回信被新问题顶掉(不覆盖) / sync-fallback 上游没有异步口退回同步(会卡) / idle 还没问。压平任意两态都会造出处置相反的处境长得一样:把 canceled 与 stale-dropped 压平,用户会以为自己按了取消;把 sync-fallback 与 running 压平,用户会一直等一个永远不动的界面。
- 【两张词表分开】ASK_PHASES 管「该去哪条出口」(async 优先 / sync 回落 / absent 不在场),ASK_RUN_STATES 管「跑到什么状态」。把这两张压成一张,「本版插件没有异步出口」与「这次问失败了」就会同形 —— 前者等升级,后者重试。
- 【派发相必须严格判 true】planAskPhase 只认 === true,undefined 与 'yes' 与 1 一律不算有异步口。理由是浏览器扩展面上这三个值都真实出现过(雪碧探测返回的往往是「有值」而不是布尔),宽松判会把「没有异步口」读成「有」,于是走进一条根本不存在的路。
- 【任务身份带会话】makeAskTaskId 收成 rp-ask 前缀加会话 id 加代际三段。为什么带会话:上游把 taskId 回填在回执里,而回执可能**跨会话**回来(用户问完就切了会话),只带代际的话两个会话各自的第 3 次会撞成同一个身份,而「两个会话的第 3 次」是两件事。会话 id 取不到时写 na 而**不写空串** —— 空串会被上游读成一个合法身份,与「没给」同形。
- 【进度读数:「没给」与「给了 0」分开】onProgress 给的 plan 与 rows 读不到时如实说「读不出 —— 不是 0 行」,不补 0。0 在本面上是合法值(第 0 条计划、已处理 0 行),补 0 会让「还没开始」显示成「已经停在第一条计划上」。
- 【异步读口接进既有契约件,不另立一份】config/memory-qa-contract.js 新增 readMemoryQaAnswerAsync,与同步版共用同一套五态与同一个 emptyQa 缺席回执。唯一新增读数是 upstreamState;取消态单列成 faceReason === 'canceled'(与「问了、扫了、没命中」的 no-answer 分开 —— 两者处置相反:前者还能再问,后者该换问法)。同步版一行未改:**上游明写 askMemoryQuestion 保持原样不迁移不删除**,它是旧插件的兼容路径。
- 【控制器:派发相一处判,代际一层管】apps/memory/memory-app.js 新增 askPastAsync 与 cancelAskNow 与 isAskingCanceled。有异步口走异步;没有走同步并在运行态里**如实报 sync-fallback**(不是假装后台跑)。旧回信由 isStale 拦下(返回 receipt 为 null),**两层保护**:上游在片间读 shouldCancel 会停掉旧那一轮(省掉白扫),即便它已经跑完了,回信也会在这里被丢弃 —— 两道都在,因为取消检查有可能迟一片生效。
- 【换会话必须换掉 tracker】onChatChanged 里把 _askTracker 置 null。理由与本仓其它会话态同源:tracker 哪怕只是一个计数器,换会话也必须换掉 —— 否则新会话的第 1 次会与上一段的第 1 次撞代际,而撞代际的表现是「新问题的答案被当成旧回信丢掉」。
- 【视图:取消按钮 + 运行态行 + 旧回信不画】问往事页新增取消按钮(默认 hidden,只在 running 期间出现)与运行态行。旧回信到达时**只显示一条提示、不重画答案**(那正是本版要治的形态)。取消态**先说「下面是已处理部分,不是全量结论」再列答案** —— 顺序反了读者会先把它当全量记住。进度回调在控制器那一侧也过代际守卫,旧那一轮的进度不许刷进新问题的进度条。
- 【本版自己抓到的缺陷形态两处,一处是判据错、一处是工具错(合并前逐条修掉,留痕)】一 C3 首版按「源码里两个名字谁先出现」判拼接次序,当场转红 —— 但真码是对的:`_askBodyHtml(r)` 是先求值再拼进 return 的,输出里它本就排在后面。判据改成读**那一条 return 的拼接式**(输出次序的真证据)。二 抬版脚本与补丁脚本的锚点三次零命中,全是标点被全角化(元信息行的冒号、版本数句的逗号、边界文档的括号与分号),以及一次把注释行当锚点 —— 三次都靠「锚点必须恰中一次」这条纪律当场抛错救回,而不是静默改错位置。
