## 迭代 239 · v4.105.0 · R13-O2 销毁动作分级（89 件三档声明 + 38 处确认守卫 + 诊断面接线 + 26 门判据）

- 【版本升至 4.105.0（五源同源）】manifest.json / package.json / index.js 版本常量与公告块 / update-log.json 的 latest 与 head 与新条目 / tests/audit/status-ledger.json 的 version 与四处 version_sources 一次抬齐；ITERATION_LOG 新增本迭代段并把元信息「当前版本」行改当版；边界文档按当版复校。抬版沿用仓内范式脚本（本次 tools/bump_v4105.py 对齐 tools/bump_v4104.py，只换 STEPS 与头注，逻辑一字未改）。
- 【治的欠债：删了能不能回来，此前全仓没有一处说得清】v4.104.0 把回收站做成唯一软删实现之后，回收站本身只回答了「我删的那一条还在不在」，回答不了用户更早的那个问题：这件 App 的删除到底是可以捞回来的，还是我一按就没了。而这两种处境在界面上长得一模一样 —— 都是同一句「删除成功」。
- 【三档不是三种实现，是三种处境】可撤销（删除先进回收站，在设置里能取回）、不可撤销但已确认（删除前有一次二次确认，用户是知情的）、不可撤销且未确认（按下去就没了，连问都不问）。第三档在本仓是真实存在的一档，不是「待办」：89 件里有 59 件落在这里。把第三档藏起来（比如只报前两档）等于替产品撒谎。
- 【声明表放在 config/undo-capability.js 的常量表里，理由是要能被机器对账】每档带 label / what / source，source 写的是这一档的判据形态：可撤销档的判据是 apps 目录里真出现回收站登记调用，已确认档的判据是那条破坏性分支里真出现 confirmDestroy，第三档的判据是两者都不出现。声明与磁盘事实必须双向对得上，否则这张表就只是人写的一段散文。
- 【89 条声明与 APPS 真源双向对账，笔数一条不差】第一次生成时表里只有 88 条，且其中两条重复（doujin 与 cheat 各出现两次）、一条是占位（zhibo-absent-guard 在 APPS 里根本没有这件 App）。对账当场报出三个读数：APPS 有而声明缺的 4 件、声明有而 APPS 无的 1 件、重复 2 条。差额不是笔误，是「表按人记得的那几件写」的必然结果。
- 【graph / clock / usage / timeweaver 四件是新增的诚实条目，各有各的理由】graph 与 memory 共用 apps 目录，而该目录里的破坏性符号只属于 memory 那几件，graph 的三件零命中 —— 这正是「按目录统计就会把 graph 算成有回收站」的那一条；clock 三件、usage 三件、timeweaver 四件在清空 / 删除 / 清除 / 重置四个词与破坏性符号上双双零命中，其中 usage 唯一一次命中是注释里那句「清洞察设置不该顺手重置主屏」的范式说明，不是入口。四条都带具体理由写进 why，why 一律不许写「不适用」。
- 【38 处确认守卫：19 个 App，逐个破坏性分支头插 confirmDestroy】扫描分四轮收敛：先按 act / action 两条写法扫出 35 点，补查发现 pvdesk 用的是 name 形，把写法面扩到四形得 43 个分支头，再逐条打印上下文人工核真伪，最后用严格的应用内破坏性调用正则配 8 行窗口定稿 38 点。守卫形态统一为一句 if 判 confirmDestroy 返回假就 return，import 行统一走 config/destructive-confirm.js。
- 【两类假销毁分支被剔除，它们不是漏扫是误报】清输入框（把内部缓冲置空）与重置内存态草稿（把草稿对象换成一个新的）都不落盘、删的也不是用户的资产，给它们加二次确认只会让清空输入框这件事变得烦人。这两条正是前一轮 40 点与本轮 38 点的差额来源，差额本身要写下来，否则下一轮会当成漏扫再补回去。
- 【可撤销性只认声明面、不认调用方】调用方当然会说自己这次可撤销（它只想少弹一个框），所以 describeDestroy 的 recoverable 只读声明表里这一件 App 的那一档，调用方传进来的 undoable 一个字都不采信。这条纪律的判据形态是反着测的：对一件不可撤销的 App 故意传 undoable 为真，它必须仍然判不可撤销、文案里必须仍然出现不可撤回。
- 【不可撤销的文案必须把「会怎样」说出来，而可撤销的文案必须指路】可撤销档的文案写的是删除后会先进设置里的回收站、在那里可以恢复；不可撤销档的文案是此操作不可撤回加上这一档的 what。条数只在拿到有效正数时才拼进文案，取不到数时不写共 N 项 —— 写一个 0 比不写更糟。
- 【诊断面接线：这条卡片要在用户准备点清空之前出现】新增的销毁分级面接进诊断中心四处（内核取值、返回对象、文案出口、视图卡片），摆在图标覆盖率卡之后。卡片标题直接写人话：89 件 App 删了能不能回来。表里只铺前两档的 id（第三档 59 件不铺，否则卡片自己就撑爆了），第三档改用一枚 warn 芯片加一个独立字段摆出来。
- 【本版自己抓到的缺陷：残留账被记成 problem，卡片会永久红】首版把「有 59 件 App 属既不可回退也没二次确认的残留账」push 进 problems，于是 ok 恒为假、这张卡永久红。自审判定这是设计缺陷：残留账是本轮如实记账的那一部分，不是这张卡坏了；而永久红比不报更糟 —— 它会训练用户忽略红。修法是 problems 只留结构性问题（声明条数与 APPS 真源不一致、双向自证失败），残留账改用 warn 芯片加独立字段，并由判据套件把它冻结成数字，59 一变动即红。
- 【本版自己抓到的缺陷形态：弱口径被本仓自己的门当场抓住】新写的诊断面里对条数写了一句 Number.isFinite 包 Number 的取数，weak-coercion 门直接报红并点出行号。这门治的正是「上游没给这一格」与「上游给了 0」在同一个读数下塌成同一件事，而两者处置相反。修法不是就地改，是走全仓唯一实现 config/num-gate.js 的 numOrNull（该文件早已 import 它），并把「这一处是本版自己写的弱口径、被门当场抓出来的」写进注释。这是本仓门禁设计意图的正面兑现，不是失误叙事。
