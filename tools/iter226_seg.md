- 【R11-X1 做了什么】把三件早已挂进中枢却产品端零读的管理器接进群像 App 的档案面：InventoryBackpackManager（随身物）、CharacterDossierManager（关系与关键记录）、VolumeChronicleManager（按时间切的卷宗回顾）。修前实测：三件在 config/subsystem-orchestrator.js 挂成 subsystems.backpack/.dossiers/.volumes，scripts/keys-audit.mjs 也逐键登记了三把落盘键，但产品端零 import、零 storage.set —— 数据没有出口，用户看不到「角色身上有什么、跟谁什么关系、前几卷发生过什么」。改造面四处：三件管理器各加 serialize()/restore()；新建 config/archive-face-bridge.js（纯读纯函数桥）；apps/chars/chars-app.js 加中枢解析口 archiveFace() 与七个写口；apps/chars/chars-view.js 加档案卡与六种操作点绑定。
- 【本版自己抓到：拼错状态永不告警，读档把历史抹掉】三件管理器此前没有任何持久化能力：背包的 items 是纯内存 Map，进程重载即空，而 keys-audit 登记的三把键从未有写入方 —— 这是最难发现的形态（键有登记、门禁全绿、用户的数据每次会话都消失）。补 serialize/restore 时抓到第二个同族隐患：恢复若走 registerItem 重新登记，每次读档都会为每件物品伪造一条 acquired 历史，把「读档」变成「再次获得」，且转赠溯源链会被二次污染。故 restore 逐条校验 id+name 后原样写 Map、history 一字不改（头注写明理由），并落 D1/G3 双判据钉住。
- 【桥的形态：纯读 + 纯函数，不是第二份真源】config/archive-face-bridge.js（158 行）不含 storage、不含持久化：mapBackpackRow / mapDossierRow / mapVolumeRow 三个纯映射，mergeArchiveFaces(hub, opts) 返 faces / counts / notes。faces 各面为 null 表示读不到（与空数组不同形），notes.mustShowWhy 为真时视图必须明写读不到，why 取值 ok|no_subsystems|no_backpack|no_dossiers|no_volumes|backpack_read_threw|dossiers_read_threw|volumes_read_threw。持久化契约归各数据主（serialize/restore 在管理器身上），写口只在本 App 的 _archiveSaveAll / _archiveRestoreAll 两处，三键一次写齐、一次读回 —— 不做只写改动那一件的半截持久化。
- 【三态不同形的具体落点】读到了有 N 条 → 正常列表带计数；读到了 0 条 → 「还没有录入物品 / 还没有登记的档案 / 还没有封存的卷宗」；读不到 → 「读不到（这是「读不到」，不是「没有物品」）」。三面各一句独立措辞，F2 判据逐句正则钉住。中枢缺席另分两档归因：宿主上没有 subsystems 记 no_host，有容器但三件缺位记 no_subsystems，两档不许压成一句坏了。
- 【每块都有可操作点（计划明文不许只读塞设置里）】背包行：转赠（改持有者并记一条 transfer 历史）、消耗或遗失（状态机 held/lost/consumed）、录入新物品；档案行：登记开档、标注性格偏移（behavior/meaning/avoidReadingAs 三段）、详情（按名直取完整档案，消费 archiveGetDossier）；卷宗行：回顾（按卷号直取 recap，消费 archiveGetVolume）并走 phone:openApp 去日记 App 按时间线翻。卷宗数据无条目 id 与楼层锚，故不造靶心 ref、不谎称已定位到楼层 —— 与 X2 不声称已跳到的口径一致，边界写进操作归因一行。
