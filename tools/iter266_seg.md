## 迭代 266 · v4.145.0 · R21-O4 覆盖率读数进账本（2026-11-13）
- 【版本升至 4.145.0（五源同源）】第二十一期批次 C 第一步 R21-O4：把「431 个测试文件、十九道门里没有一道读过覆盖率」这笔账收成可读的一页 —— 覆盖率不是没量过，是量完没人看、下次量完不和上次比，等于没量。
- 【只做不许退步，不设绝对下限】判据只有两条：任一 app 目录的行覆盖降幅超过 0.5pp 即红，零测试目录数从 10 涨到 11 即红。绝不写「整体必须 80%」那种数 —— 本仓整体行覆盖实测 60.95%，写 80 等于当天造一道恒红门；恒红的门下场只有一个，被人 SKIP。
- 【三列读数落到账本，目录集合以磁盘为准】tests/audit/coverage_baseline.json 记 101 个 app 目录的 line_pct / files_with_test / zero_test_files，另有全仓 totals（437 个盘上文件、115 个零覆盖文件、10 个零测试目录、2483 条覆盖行）。判据 E3 钉住账本目录集合必须与磁盘 apps 目录集合逐项相等 —— 新 app 不写测试，账本不认它是「自动 100%」。
- 【行加权而非百分比平均】整仓 60.95% 是行加权结果，直接对 101 个目录的百分比取算术平均会得到另一个更大的数（小文件权重被放大）。lib 里按「已覆盖行数 = 百分比乘总行数再除一百」的等价式反解覆盖行数再加权（U 为 0 时记 unknownWeight，不假装 0 权重悄悄消失），故 A1 判据要求两者不等且确实算出行权重。
- 【本版自己抓到的缺陷形态一：正则把分隔空格也吃掉了】spec 覆盖段的缩进语义是「ℹ 之后的空格数即层级」，首稿用「信息符 + 空白类 + 捕获组」的写法，让空白类转义先吃掉那一个分隔空格再数剩余空格，于是顶层段 apps 得 depth 0 被当成无效行丢弃、路径栈建不起来、437 个文件全被误判零覆盖（首次 --write 打印的正是「零覆盖文件 437」）。改成「信息符 + 捕获组」的写法后层级恢复正常，文件数从 437 假读数回到 115 真读数。这条是本版最值钱的一次自查：错的不是判据，是判据赖以成立的那个解析器。
- 【本版自己抓到的缺陷形态二：负控制差一点成了假对照】D2 首稿按覆盖率降序取前三个目录各抬 10pp，可这三个目录本就接近或等于 100%，Math.min(100, p + 10) 抬不动，drop 恒为 0，门照旧判 pass —— 负控制自己先绿了，那它还验什么。现改为只挑 20% 到 80% 区间里抬得动的目录（本版实测选中 diagnose 79.63 / uterus 79 / kettle 77.96），并在判据注释里把这个反面教训写死，下一个改它的人不必重踩。
- 【本版自己抓到的缺陷形态三：all files 汇总行被当成文件行】spec 表末尾有一行 all files 汇总，同样带三个百分数，首稿的解析把它算进了文件行，B1 于是「必须解析出 1 条文件行，实得 2」。改为显式排除 all files 之后，文件行与目录行才互不污染。同一族的写法问题还有 C3 的多层转义：判据里用正则去匹配一段本身含正则的源码，转义层数一错就永远匹配不上，最后改成 includes 逐字包含，不跟转义较劲。
- 【交棒改写：门拆两档，因为十一分钟不能塞进每版都跑的链】全量 node --test --experimental-test-coverage 实测 653 秒（6407 例全绿）。若把它原样接进 npm run check，每版每条链都要多等十一分钟，人人会拿 SKIP 绕过，门等于没有。故本门拆两档：默认（无参）只跑结构自检（账本 schema 在位、drop_pp 与常量同源、账本目录集合与磁盘 apps 相等、TODO 欠账段与账本同源、note 两条诚实边界仍在），实测 673ms；--verify 才真跑或配合 --from 离线复算并判退步。判据 C2 专门钉住脚本键不许带 --verify、默认档必须直落 selfCheck，防下一个人「顺手」把它接成重门。
- 【读数与真跑必须能对上，且要留第二证人】单靠账本自证是循环论证。故 D1 要求仓库内保留 tests/audit/coverage_source.log（真跑的 spec 覆盖段，630703 字节），判据从这份日志离线复算 101 个目录、2483 条行，逐项与账本比对，差一个字都红；日志不在场则直接 assert.fail 拒判，不许「没证据也算过」。
- 【欠账清单由生成器写，不手抄】TODO.md 的覆盖率欠账段由 --write 一并重写，B6 判据要求渲染结果可复算、且拼接函数幂等（同一份账本连续拼两次文本不变）。手抄的清单第一次写对、第三次必漂，这是仓内早已有的教训。
- 【运行时验证边界】本版量的是 Node 层的 V8 行/分支/函数覆盖，不含浏览器层：tests/browser/ 下 20 个场景、4 个视口的行为由 v4.100.0 的浏览器门与冻结失败账本另管，Node 覆盖读数对它们一言未发。覆盖率为 0 也不等于代码不可达（大量入口只在真宿主注入后才被点亮），反过来高覆盖率也不证明真机表现正确。账本 note 里这两条诚实边界由判据 E2 钉住不许被抹掉。
